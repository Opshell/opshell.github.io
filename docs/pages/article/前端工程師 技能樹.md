::: info 這篇的脈絡
打開中高階前端的職缺，常常會看到一串十幾條的要求：精通這個、熟悉那個、具備什麼經驗尤佳。第一次看的人會覺得這是在徵超人；看久了會發現，這張清單其實只是門票。
這篇想把那串清單拆開：哪些是基本功、面試真的會往下挖哪些題目，以及清單上沒寫、但決定你是不是「中高階」的那件事。寫給正在往中高階走、或正在準備面試的前端工程師。
:::

## 懶人包

- 職缺上那十幾條技能，我認為-|全部都是中高階的必備知識|-，但它只是門票，不是天花板。
- 面試真正會往下挖的，是清單背後的「為什麼」：請求怎麼取消、打包怎麼切、Token 怎麼換、型別怎麼管。
- 中高階最後被看重的不是會幾個框架，而是能不能回答三個問題：怎麼幫團隊省錢、怎麼省時間、怎麼讓人信任這個團隊。
- 交付是第一優先，避免過度工程化；這件事 *The Pragmatic Programmer* 講得比我好。

## 觀點拆解

### 第一層：清單上的基本功

這是一份很典型的中高階前端要求，我把它原封不動放上來：

1. 精通 TypeScript 及常用框架（如 React、Vue）和相關套件。
2. 熟練掌握 HTML5、CSS3 及主要樣式庫（如 MUI、TailWind CSS、Ant Design）。
3. 深入理解 RESTful、GraphQL、WebSocket、SSE 等通訊協議，並掌握合規的認證與授權技術。
4. 熟悉版本控制、效能測評（如 Core Web Vitals、Lighthouse、Page Speed Insights），以及前端測試工具（如 Jest、Mocha、Cypress、Selenium）和 Git 的應用。
5. 了解瀏覽器渲染、儲存與交互技術及外掛開發，能夠優化兼容性和分散處理。
6. 掌握狀態管理工具（如 Redux、Vuex），能夠構建高效的狀態機與資料流。
7. 能根據需求進行模組化與元件化開發，實現 Module Federation，提升代碼的可維護性和重用性。
8. 具備識別和解決性能瓶頸的能力，能應用代碼分割、Lazy Loading、資源預加載、CDN 等技術，確保應用的高效運行。
9. 熟悉前端安全性措施，如 XSS 防護、CSRF 防護、Content Security Policy（CSP），能有效保護應用和用戶數據。
10. 具備跨平台與移動端開發經驗（Cross-Platform & Mobile Development）。
11. 熟練撰寫清晰的前端技術文檔和測試文檔，確保開發過程透明且可追溯。
12. 具備良好的溝通能力，樂於團隊合作和分享技術新知，並熱愛編程，致力於寫出更優質的代碼。
13. 具備同時執行多個專案並能有效應對時程壓力的心態與能力，熟悉 Agile SDLC 尤佳。
14. 具備重構老舊架構與代碼的豐富經驗，以及從無到有獨立完成前端專案上線的經驗者尤佳。

這些全部都是中高階必備知識。看起來很嚇人，但仔細看，它其實是在問三件事：**你寫得出來嗎（1、2、6、7）、你寫得好嗎（4、5、8、9）、你跟人合作得來嗎（11～14）**。

::: tip 2026 年讀這份清單
清單裡的工具名稱會過期，概念不會。Vue 的狀態管理現在是 `Pinia`，`Vuex` 已經進入維護模式；單元測試在 Vite 專案裡多半用 `Vitest`，E2E 則是 `Playwright` 跟 `Cypress` 的天下。面試時講得出「為什麼換」，比背得出工具名稱有用。
:::

### 第二層：面試會往下挖的題目

清單上每一條，都能被追問到很深。下面這些是我覺得很能分出程度的題目：

- **QPS 優化（Abort Controller）**：使用者狂打字，搜尋 API 被打爆，你怎麼辦？
- **打包粒度和預處理**：chunk 要切多細？切太碎跟切太粗各會發生什麼事？
- **SSR 的 Refresh Token 機制設計**：伺服器端渲染的時候 Token 過期了，誰來換？換完怎麼同步回瀏覽器？
- **動態組件引入與 Suspense**：非同步元件載入中、載入失敗，畫面要長什麼樣？
- **zod + ts-rest 建置一個可以讓前後端並行快速開發的專案架構**：後端 API 還沒好，前端怎麼不用等？
- **Feature Based 架構與 Feature Sliced Design 的不同**：一個是「按功能分資料夾」，一個是「有層級與依賴規則的方法論」。
- **有效管理 TS type/interface 的方式**：型別放哪、誰擁有、怎麼避免同一個型別定義三次。
- **迭代與遞迴的選用**：可讀性、效能跟堆疊深度之間怎麼取捨。

這些題目沒有標準答案，面試官想聽的是你的取捨過程。~~（背答案的人，第二個追問就會露餡。）~~

### 第三層：清單上沒寫，但真正被看重的

技能清單講的是「你會什麼」；但走到中高階，別人真正在意的是「你能幫團隊做到什麼」。我把它濃縮成三個問題。

#### 1. 怎麼省錢

- 圖片壓縮
- CDN、gzip
- QPS 優化
- 打包 size
- 適時每段時間調整購買的機器等級（雖然這是 OPS 的事情）

前端的每一個 byte、每一次請求，最後都會變成帳單上的數字。會算這筆帳的前端，在老闆眼裡跟只會刻畫面的前端，是兩種人。

#### 2. 怎麼省時間

- mock server 與 zod + ts-rest 協作，前後端可以同時開工
- feature based 架構，很容易知道東西發生問題爛在哪，溯源方便
- 其他任何當時的時空背景下最小可行、修改最少的方案

最後一條最重要，也最容易被忽略。技術選型不是在選「最好的」，而是在選「這個時間點、這個團隊、這個期限下最划算的」。

#### 3. 怎麼讓人家信任這個開發團隊

- 有訂製良好的寫作規範
- 可以快速對應問題
- 有足夠彈性的擴充空間
- 能清楚知道團隊內每個人都在幹嘛
- 每個人都知道交付是第一優先，避免過度工程化

信任這件事很像存錢，平常一點一點存，出事的時候才領得出來。規範、回應速度、透明度，都是在存款；過度工程化則是在偷偷提款——花了很多時間，交出來的東西別人看不懂也用不到。

關於這個，可以去讀一下《The Pragmatic Programmer》。

## 例子與對比

### 用一個 AbortController 同時回答「省錢」跟「實力」

拿第二層的第一題來說：搜尋框每打一個字就發一次請求，使用者打「typescript」會打出 10 個請求，但只有最後一個有用。前面 9 個不只浪費後端資源（錢），還可能比最後一個晚回來，把畫面蓋成舊結果（bug）。

原生的 `AbortController` 就能解：

```ts
let controller: AbortController | null = null;

export async function search(keyword: string): Promise<string[]> {
    // 新的搜尋開始，先取消上一個還沒回來的請求
    controller?.abort();
    controller = new AbortController();

    try {
        const response = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
            signal: controller.signal
        });

        if (!response.ok) {
            throw new Error(`搜尋失敗：${response.status}`);
        }

        return await response.json() as string[];
    } catch (error) {
        // 被我們自己取消的請求不是錯誤，安靜地結束就好
        if (error instanceof DOMException && error.name === 'AbortError') {
            return [];
        }

        throw error;
    }
}
```

| | 只會「把功能做出來」 | 中高階會多想的 |
| --- | --- | --- |
| 搜尋框 | 每次輸入就打 API | 搭配 debounce 減少請求，再用 `AbortController` 取消過期的請求 |
| 結果順序 | 誰晚回來誰蓋畫面 | 舊請求被取消，畫面只會是最後一次的結果 |
| 取消的錯誤 | 跳出錯誤提示嚇使用者 | 分得出「被取消」跟「真的失敗」 |
| 成本 | 沒想過 | 知道每個多餘的請求都會反映在 QPS 跟帳單上 |

同一段程式，你可以把它講成「我會用 `AbortController`」，也可以把它講成「我幫團隊省了九成的無效請求，還順便修掉一個競態 bug」。後者才是中高階的說法。

## 結論

職缺上那串技能清單，要會，但不要被它嚇到，也不要以為全部打勾就等於中高階。清單是門票；面試的追問在看你懂不懂「為什麼」；而真正讓人想跟你共事的，是你能不能替團隊省錢、省時間，並且讓人放心把事情交給你。

技能樹點滿很帥，但記得：-|會交付的那棵樹，才結得出果子|-。
