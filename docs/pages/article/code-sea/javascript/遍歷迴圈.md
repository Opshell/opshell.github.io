::: info 這篇的脈絡
「`forEach` 好還是 `for...of` 好？」大概是前端聊天群組裡最常吵起來的題目之一，吵到最後通常會變成宗教戰爭。這篇把一次這類討論的觀點整理起來，加上我自己的偏好，寫給還在糾結「到底該用哪個」的人。
:::

## 懶人包
- 每一種風格指南都有對應的偏好，像 `Airbnb` 風格就禁止 `for...of`，但方法沒有對錯，看應用場景。
- 一般業務程式碼用 `forEach`、`map` 就好，可讀性優先；性能敏感、需要 `continue`、`break` 的場合才換 `for...of`。
- 拿超大陣列的測試結果去否定 `forEach` 不太公平，真的嫌大包資料慢，就拉去 `Web Worker`。
- 遍歷物件時要知道每個方法抓得到哪些 key：想連 `Symbol` 一起拿，用 `Reflect.ownKeys`。

## 觀點拆解

### 風格指南各有偏好，但方法沒有對錯
我覺得每一種風格都有對應的偏好。像 `Airbnb` 的 `ESLint` 設定就用 `no-restricted-syntax` 禁止了 `for...of`（連 `for...in` 一起），理由是希望大家用 `map`、`filter`、`reduce` 這類高階函式，寫出沒有副作用的程式。

這個理由沒錯，但它是「一種偏好」，不是「唯一真理」。迴圈就像交通工具：去巷口買早餐騎腳踏車，跨縣市搬家叫貨車，你不會因為貨車比較會載就騎貨車去買蛋餅。

### 我的分法：forEach 為主，for...of 救場
我只有在性能敏感、需要 `continue`、`break` 的場合才會用 `for...of`，其他地方還是用 `forEach`。

`forEach` 沒辦法中途跳出（`return` 只是結束這一次的 callback），想要「找到就停」的時候，硬用 `forEach` 只會越寫越彆扭：

```ts
// forEach：找到了也停不下來
let found: User | undefined;
users.forEach((user) => {
    if (!found && user.id === targetId) {
        found = user;
    }
});

// for...of：找到就走
let target: User | undefined;
for (const user of users) {
    if (user.id === targetId) {
        target = user;
        break;
    }
}
```

~~當然，這個例子最好的答案是 `users.find()`，但那就不能拿來吵架了。~~

### 小陣列比速度，沒有意義
常聽到一種說法是「`forEach` 在小陣列比 `for` 還要快速」，也有人反過來說 `forEach` 慢。現在的 `JavaScript` 引擎都會對熱點程式碼做 JIT 最佳化，小陣列上幾種迴圈的差距小到幾乎量不出來，-|在這個量級比速度，不如比誰比較好讀|-。

反過來，直接用大陣列很慢就打翻 `forEach`，我也覺得不公平。`forEach` 每個元素多一次函式呼叫，資料一大成本確實會浮出來，但那是「場合選錯」，不是工具爛。

聊天時聽過一個經驗：某個共用的計算模組，單純把 `forEach`、`map` 之類的方法換成一般的 `for...of`，性能就直接提升了 10 倍左右。當然，一般寫業務還是用 `forEach`、`map`。

總的來說，迴圈這種東西，如果你要搞 DFS、很深的資料又有上千筆，才去考慮用 `for...of` 取代 `forEach` 和 `map`，因為這時候要考慮的就是迭代成本。

真的嫌大包資料慢？就拉去 `Web Worker` 嘛（挖鼻）。主執行緒是拿來畫畫面的，不是拿來算帳的。

### 其實我更喜歡 while
我個人⋯⋯⋯覺得 `for` 很醜 XD。寫那個 `i < a; i++` 很煩躁，對，很討厭。

我其實更喜歡 `while`。迭代還可以不用管遞迴的問題（堆疊自己管，不會撞到呼叫堆疊上限，詳見 [二元樹走訪](./二元樹)），搭配 `i--` 從尾巴往前走，還順便解決了一個經典的坑：邊遍歷邊刪除元素時，從後面刪不會影響到前面還沒走到的索引。

```ts
let i = list.length;
while (i--) {
    if (list[i].disabled) {
        list.splice(i, 1);
    }
}
```

## 例子與對比

### 陣列：什麼時候用哪個

| 寫法 | 能 break / continue | 適合 |
| :--- | :--- | :--- |
| `forEach` | 不行 | 一般業務邏輯、有副作用的逐筆處理 |
| `map` / `filter` / `reduce` | 不行 | 從舊陣列算出新陣列 |
| `find` / `some` / `every` | 會自己提早結束 | 找東西、判斷條件 |
| `for...of` | 可以 | 要提早跳出、`await` 逐筆執行、大資料 |
| `for` / `while` | 可以 | 要控制索引、倒著走、極致效能 |

### 物件：Object.keys 還是 for...in？
另一個常被問的問題：要去 loop 一個物件，會使用 `Object.keys` 還是 `for...in`？

我會用 `Reflect.ownKeys`。因為 `Object.keys` 抓不到 `Symbol`，而 `for...in`、`Object.keys()`、`Object.getOwnPropertyNames()` 這三種方法都無法抓出 `Symbol`。

四個方法其實各抓各的，直接看對照：

```ts
const sym = Symbol('s');
const proto = { inherited: 1 };
const obj = Object.create(proto);
obj.own = 1;
obj[sym] = 2;
Object.defineProperty(obj, 'hidden', { value: 3, enumerable: false });

const forInKeys: string[] = [];
for (const key in obj) {
    forInKeys.push(key);
}

console.log(forInKeys); // ['own', 'inherited']
console.log(Object.keys(obj)); // ['own']
console.log(Object.getOwnPropertyNames(obj)); // ['own', 'hidden']
console.log(Reflect.ownKeys(obj)); // ['own', 'hidden', Symbol(s)]
```

| 方法 | 原型鏈上的 | 不可列舉的 | Symbol |
| :--- | :--- | :--- | :--- |
| `for...in` | 會（可列舉的） | 不會 | 不會 |
| `Object.keys()` | 不會 | 不會 | 不會 |
| `Object.getOwnPropertyNames()` | 不會 | 會 | 不會 |
| `Reflect.ownKeys()` | 不會 | 會 | 會 |

`for...in` 是唯一會往原型鏈上爬的，這也是它常被風格指南禁掉的原因：一不小心就會遍歷到繼承來的東西。一般的資料物件（API 回來的 JSON）沒有 `Symbol` 也沒有怪原型，用 `Object.keys`、`Object.entries` 就很夠；需要「物件自己身上所有的 key，一個都不能漏」的時候，才請 `Reflect.ownKeys` 出場。

## 結論
迴圈的選擇跟穿衣服很像：沒有一件衣服適合所有場合，但你一定知道去海邊不要穿西裝。先寫好讀的，量出瓶頸了再換，比一開始就為了不存在的十萬筆資料犧牲可讀性實在多了。

至於 `for` 很醜這件事，我是認真的。
