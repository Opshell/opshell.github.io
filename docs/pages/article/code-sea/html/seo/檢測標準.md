網站上線前，常見的情況是 PM 或客戶丟來一張 PageSpeed Insights 的截圖：「為什麼手機版只有 52 分？」這時候要能說清楚哪些數字是 Google 真的在看的、哪些只是參考，以及該從哪裡改起。這篇整理這套檢測標準的讀法。

檢測工具：<https://pagespeed.web.dev/>
:::

## 懶人包
- PageSpeed Insights 會給兩種數據：上方是真實使用者的數據（Field Data），下方是 Lighthouse 模擬跑出來的（Lab Data）。-|Google 排名參考的是真實使用者那份|-。
- Core Web Vitals 三項：LCP（主要內容多久出現）、INP（互動多快有反應）、CLS（畫面會不會亂跳）。
- 及格線：LCP 2.5 秒內、INP 200 毫秒內、CLS 0.1 以下，以 75% 使用者的體驗為準。
- Lighthouse 的 0～100 分是實驗室分數，拿來找問題很好用，但不要把它當 KPI 追滿分。

## 技術拆解

### 兩種數據，差在哪
打開 PageSpeed Insights 跑一次，頁面會分成兩塊：

| | 真實使用者數據（Field） | 實驗室數據（Lab） |
|---|---|---|
| 來源 | Chrome 使用者回報的實際體驗（CrUX） | Lighthouse 在模擬的手機、網速下跑一次 |
| 時間範圍 | 過去 28 天 | 現在這一次 |
| 會不會每次都不一樣 | 穩定 | 會浮動 |
| 新網站有沒有 | 流量不夠就沒有 | 一定有 |
| 用途 | 判斷「使用者實際感受」 | 找出「哪裡可以改」 |

實驗室數據像是在健身房量的體能測驗，條件固定、方便比較；真實數據是你平常爬樓梯喘不喘，比較準但要時間累積。

### Core Web Vitals 三項指標

**LCP（Largest Contentful Paint）**：畫面上最大的那塊內容（通常是主圖或標題）出現的時間。代表「使用者覺得頁面載入好了沒」。

**INP（Interaction to Next Paint）**：使用者點擊、輸入之後，畫面多久有反應。2024 年取代了舊的 FID，FID 只量第一次互動的延遲，INP 則看整個造訪過程中的互動。

**CLS（Cumulative Layout Shift）**：畫面元素意外移動的程度。最經典的就是要點按鈕的瞬間上面的廣告載入，把按鈕擠下去，結果點到別的東西。

| 指標 | 良好 | 需要改善 | 不佳 |
|---|---|---|---|
| LCP | ≤ 2.5 秒 | ≤ 4 秒 | > 4 秒 |
| INP | ≤ 200 毫秒 | ≤ 500 毫秒 | > 500 毫秒 |
| CLS | ≤ 0.1 | ≤ 0.25 | > 0.25 |

判定標準是 75 百分位：-|75% 的造訪達到「良好」|-，這項才算過。

### Lighthouse 的四大分類
Lab Data 那邊還有四個分數：效能（Performance）、無障礙（Accessibility）、最佳做法（Best Practices）、SEO。這四個都是「檢查清單」性質，告訴你有哪些項目沒做到，例如圖片沒有 `alt`、按鈕沒有可讀的名稱、沒有 `meta description`。

效能分數是好幾個指標加權算出來的，其他三個比較接近「通過幾項」。改無障礙和 SEO 的項目通常很快，CP 值很高。

## 例子與對比

### 分數不好，先改哪裡

| 問題 | 常見原因 | 先試試 |
|---|---|---|
| LCP 太慢 | 主圖太大、太晚開始下載 | 壓縮成 WebP／AVIF、主圖加 `fetchpriority="high"`、不要對首屏圖片 lazy load |
| LCP 太慢 | 阻塞渲染的 CSS、JS | 外部 script 加 `defer`、只載入首屏需要的 CSS |
| INP 太差 | 點擊後主執行緒被長任務卡住 | 拆分大量運算、把不急的工作延後 |
| CLS 太高 | 圖片、廣告、嵌入內容沒預留空間 | 圖片寫 `width`、`height` 或 `aspect-ratio`，字型用 `font-display` 並選相近的備用字型 |

圖片預留空間是最便宜的修法：

```html
<!-- 瀏覽器在圖片下載前就知道比例，先把位置留好 -->
<img src="/images/hero.webp" width="1200" height="630" alt="產品主視覺" fetchpriority="high">
```

### 追分數 vs 追體驗
常見的誤區是為了把 Lighthouse 刷到 100 分，做一些對使用者沒幫助的事，例如把重要的圖片延後到使用者捲動才載入，分數漂亮了，使用者反而先看到一片空白。

我的建議是：Field Data 的 Core Web Vitals 三項都綠燈，就是及格了；Lab 分數拿來找出具體可以改的項目，而不是目標本身。

## 結論
PageSpeed Insights 的報告很長，但真正要記住的就三個數字和一個原則：LCP、INP、CLS，看真實使用者的那份。剩下的紅字是待辦清單，不是成績單。

分數是體檢報告，不是選美比賽，健康就好，不用每項都滿分。
