## 懶人包
- 無障礙和 SSR 沒有直接關係，重點是 a11y 標準（WCAG）有沒有做到。
- ARIA 的第一原則：元素本身已經有語意（`<button>`、`<nav>`），就不需要再加 `role`。
- 沒有文字內容的元素（只有圖示的按鈕、`X` 關閉鈕）要用 `aria-label` 補上名稱。
- 裝飾用的圖示或元素用 `aria-hidden="true"` 讓閱讀器跳過；裝飾用的 `<img>` 則是 `alt=""`。
- 檢測工具：axe-core、WAVE、Lighthouse，台灣的公部門案還會看 Freego。

## 技術拆解

### 無障礙跟 SSR 是兩回事
SSR 影響的是「HTML 什麼時候到瀏覽器」，跟搜尋引擎、首屏速度比較有關。無障礙關心的是「HTML 長什麼樣子」：螢幕閱讀器能不能讀懂、鍵盤能不能操作、顏色對比夠不夠。

一個 CSR 的網站可以做得很無障礙，一個 SSR 的網站也可以滿滿都是 `<div @click>`。兩者沒有直接關係，重點在 a11y 標準。國際上的標準是 W3C 的 WCAG，台灣政府網站的無障礙規範也是以 WCAG 為基礎，細節以官方公告為準。

### 有語意的元素不需要 role
元素的名稱已經包含語意，就不用再加 `role`：

```html
<!-- 多此一舉 -->
<button role="button">送出</button>
<nav role="navigation">...</nav>

<!-- 這樣就好 -->
<button type="button">送出</button>
<nav>...</nav>
```

`<button>` 本身就是按鈕，標示已經很足夠。`role` 是給「本來沒有語意的元素」補語意用的，例如不得已要用 `<div>` 做按鈕時。但更好的做法是一開始就用對標籤，`<div role="button">` 還得自己補 `tabindex`、Enter／空白鍵觸發，用 `<button>` 這些都是內建的。

### 沒有文字的元素：aria-label
螢幕閱讀器讀按鈕時，讀的是按鈕裡的文字。只有圖示的按鈕，閱讀器只會說「按鈕」，使用者不知道它是做什麼的。這時用 `aria-label` 補上名稱：

```html
<button type="button" aria-label="搜尋">
    <i class="icon-search" aria-hidden="true"></i>
</button>
```

dialog 那種彈窗上的關閉鈕，如果只是個 `X`，閱讀器會念出「X」或「乘號」，一樣要補：

```html
<button type="button" aria-label="關閉">X</button>
```

注意 `aria-label` 要寫它-|做的事|-。關閉彈窗就寫「關閉」，真的是刪除資料的按鈕才寫「刪除」，不然使用者按下去會嚇一跳。

### aria-label 還是 aria-labelledby
兩個都是給元素一個「名稱」，差別在名稱從哪裡來：

```html
<!-- aria-label：直接寫字串 -->
<button type="button" aria-label="關閉">X</button>

<!-- aria-labelledby：指向畫面上已經存在的文字 -->
<div role="dialog" aria-labelledby="dialog-title">
    <h2 id="dialog-title">刪除確認</h2>
    ...
</div>
```

我的判斷方式：-|畫面上已經有可以當名稱的文字，就用 `aria-labelledby` 指過去|-，文字改了名稱會自動跟著改，也不會有兩份文字不同步的問題；畫面上沒有可見文字（純圖示按鈕），才用 `aria-label`。所以 `aria-label` 比較常用，是因為純圖示按鈕比較常見，不代表它比較好。

### 裝飾用的元素：aria-hidden
純裝飾用的小圖示或元素，用 `aria-hidden="true"` 讓閱讀器不讀它：

```html
<i class="icon-star" aria-hidden="true"></i>
```

上面搜尋按鈕裡的圖示也加了 `aria-hidden`，因為按鈕的名稱已經由 `aria-label` 提供，圖示再被讀一次只是噪音。

我自己會把 `aria-hidden` 用在裝飾性的圖片上。不過如果是 `<img>` 標籤，還有更正確的寫法：裝飾用的圖片給空的 `alt`，閱讀器就會跳過它。

```html
<!-- 有意義的圖片：寫出內容 -->
<img src="/images/chart.png" alt="2025 年各季營收長條圖，第四季最高">

<!-- 裝飾用的圖片：空 alt -->
<img src="/images/divider.png" alt="">
```

### SEO 檢查時要求的 aria-label
Google 的 Lighthouse 檢查有時會要求補上 `aria-label`，通常發生在兩種元素：圖片和按鈕。原因就是上面講的「沒有可讀的名稱」。另外一個常見來源是第三方 SDK：範例程式碼裡如果有沒文字的按鈕，通常官方範例就會寫好 `aria-label`，複製過來時別把它刪了。

## 例子與對比

### 檢測工具
自動化工具抓得到的大概是一部分問題（缺 `alt`、對比不足、沒有名稱的按鈕），鍵盤操作順序、閱讀器念出來通不通順，還是要自己實際操作一遍。

| 工具 | 形式 | 適合 |
|---|---|---|
| axe-core | 函式庫、瀏覽器擴充 | 整合進測試流程，CI 自動檢查 |
| WAVE | 瀏覽器擴充、線上工具 | 在頁面上直接標出問題位置，好理解 |
| Lighthouse | Chrome DevTools 內建 | 快速看個大概，順便看效能與 SEO |
| Freego | 台灣政府提供的檢測工具 | 公部門網站申請無障礙標章時使用，規範以官方為準 |

### 台灣實務上會注意 WAI-ARIA Roles 嗎
老實說，一般商業專案很少有人逐一檢查 ARIA roles，大部分團隊做到「用對語意標籤、圖片有 `alt`、按鈕有名稱」就已經比平均好了。

需要認真看 roles 的情況主要是兩種：一是公部門或有無障礙要求的案子，要通過檢測；二是自己刻複雜元件（下拉選單、分頁籤、樹狀選單），這些元件沒有對應的原生標籤，只能靠 `role="tablist"`、`role="menu"` 加上對應的 `aria-*` 狀態來告訴閱讀器。這部分可以參考 W3C 的 ARIA Authoring Practices Guide，裡面每種元件都有完整範例。

## 結論
無障礙的起點不是 ARIA，而是 HTML 本身：用對標籤，大部分的語意就已經有了。ARIA 是補洞用的，沒文字的按鈕補名稱、裝飾的元素藏起來、自刻的元件補角色。補洞的原則只有一個：沒有語意才補，有語意就別畫蛇添足。

無障礙不是做給少數人的額外功能，而是讓網站在各種情況下都能用。順帶一提，做好了 SEO 分數也會跟著漲，算是額外的獎勵。
