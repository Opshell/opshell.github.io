::: info 這篇的脈絡
登入、送出表單、刪除確認這類流程，很容易寫成「成功的話……再成功的話……再再成功的話……」的俄羅斯娃娃。功能是對的，但下一個人（或下個月的自己）要讀懂，得一層一層剝開。
這篇拿一段常見的登入處理當例子，一步一步把它攤平，寫給還在跟巢狀 if 搏鬥的人。
:::

## 懶人包
- 巢狀越深，讀的人腦袋裡要同時記住的條件就越多；可讀性差，通常不是因為邏輯難，而是因為縮排深。
- **提前返回（early return）**：先把失敗的情況處理掉、`return`，主要流程就能貼著左邊寫完。
- **重複的錯誤處理抽成一個函式**，以後要改通知方式只改一個地方。
- 能用 `async/await` 就別再 `.then()` 裡面包 `if`，流程會更像在讀一段普通的程式碼。
- 重構完一定要逐行對照原版：最常見的事故不是寫不漂亮，是**不小心少了一行**。

## 技術拆解

### 為什麼巢狀難讀

讀程式碼就像聽人講路：「直走，看到便利商店的話右轉，如果便利商店是全家就再左轉，不是全家的話……」講到第三層，聽的人已經忘了一開始要去哪。

巢狀 `if` 也一樣。每多一層，讀的人就要多記一個「目前在什麼條件下」。更麻煩的是 `else` 會離它的 `if` 越來越遠，最外層的錯誤處理，往往要捲到最底下才看得到。

### 優化建議

1. **減少巢狀結構**：巢狀過深會降低可讀性，可以透過提前返回來減少巢狀層級。
2. **重構錯誤處理邏輯**：每個錯誤處理都包含一樣的通知邏輯和 `isLoging.value = false`，把重複的部分抽成一個函式。

### 為什麼要這樣優化

1. **提高可讀性**：減少巢狀結構，失敗的情況和主要的業務邏輯分開，主流程一眼就看得完。
2. **減少重複程式碼**：錯誤處理集中在一個函式裡，程式碼更簡潔。
3. **更容易維護**：未來要改錯誤處理（例如換一套通知元件），只要改一個地方，出錯的機會也變少。

## 例子與對比

### 原版：四層的俄羅斯娃娃

```ts
sendRequest(url, 'POST', loginForm).then((auth) => {
    if (auth) {
        if (auth.status) {
            if (auth.access_token) {
                userStore.setToken(auth.access_token);

                userStore.signIn({ ...auth.data, access_token: auth.access_token });

                // 導向來源 或者 首頁
                const redirect = route.redirectedFrom?.fullPath || '/';

                router.push({ path: redirect });
            } else {
                proxy.$notify('error', '登入失敗！', 'Token 缺失！！').then(() => {
                    isLoging.value = false;
                });
            }
        } else {
            proxy.$notify('error', '登入失敗！', auth.msg).then(() => {
                isLoging.value = false;
            });
        }
    } else {
        proxy.$notify('error', '登入異常！', '網路錯誤！！').then(() => {
            isLoging.value = false;
        });
    }
});
```

注意看「網路錯誤」這個最外層的情況，它的處理被擠到了最底下，跟它的 `if (auth)` 隔了二十幾行。

### 第一步：提前返回

把三個失敗的情況各自處理完就 `return`，剩下的就是成功的路：

```ts
sendRequest(url, 'POST', loginForm).then((auth) => {
    if (!auth) {
        proxy.$notify('error', '登入異常！', '網路錯誤！！').then(() => {
            isLoging.value = false;
        });
        return;
    }

    if (!auth.status) {
        proxy.$notify('error', '登入失敗！', auth.msg).then(() => {
            isLoging.value = false;
        });
        return;
    }

    if (!auth.access_token) {
        proxy.$notify('error', '登入失敗！', 'Token 缺失！！').then(() => {
            isLoging.value = false;
        });
        return;
    }

    userStore.setToken(auth.access_token);
    userStore.signIn({ ...auth.data, access_token: auth.access_token });

    // 導向來源 或者 首頁
    const redirect = route.redirectedFrom?.fullPath || '/';
    router.push({ path: redirect });
});
```

檢查的順序也跟著變得很好讀：有回應嗎？成功嗎？有 token 嗎？三關都過了才登入。

### 第二步：把重複的錯誤處理抽出來

三個錯誤區塊長得一模一樣，只差標題和訊息，抽成 `handleError`：

```ts
sendRequest(url, 'POST', loginForm).then((auth) => {
    const handleError = (title: string, message: string) => {
        proxy.$notify('error', title, message).then(() => {
            isLoging.value = false;
        });
    };

    if (!auth) {
        handleError('登入異常！', '網路錯誤！！');
        return;
    }

    if (!auth.status) {
        handleError('登入失敗！', auth.msg);
        return;
    }

    if (!auth.access_token) {
        handleError('登入失敗！', 'Token 缺失！！');
        return;
    }

    userStore.setToken(auth.access_token);
    userStore.signIn({ ...auth.data, access_token: auth.access_token });

    // 導向來源 或者 首頁
    const redirect = route.redirectedFrom?.fullPath || '/';
    router.push({ path: redirect });
});
```

### 第三步：換成 async/await

`.then()` 本身也是一層縮排。整段包成一個 `async` 函式，主流程就完全貼著左邊了：

```ts
function loginFailed(title: string, message: string) {
    proxy.$notify('error', title, message).then(() => {
        isLoging.value = false;
    });
}

async function loginHandler() {
    const auth = await sendRequest(url, 'POST', loginForm);

    if (!auth) return loginFailed('登入異常！', '網路錯誤！！');
    if (!auth.status) return loginFailed('登入失敗！', auth.msg);
    if (!auth.access_token) return loginFailed('登入失敗！', 'Token 缺失！！');

    userStore.setToken(auth.access_token);
    userStore.signIn({ ...auth.data, access_token: auth.access_token });

    // 導向來源 或者 首頁
    router.push({ path: route.redirectedFrom?.fullPath || '/' });
}
```

三行檢查、三行做事，從上讀到下就結束了。

::: warning 重構最怕少一行
這段程式碼第一次攤平時，`userStore.signIn(...)` 那一行其實被弄丟了：畫面照樣跳轉，token 也存了，但使用者資料沒寫進 store，要到某個頁面讀使用者名稱才會爆。
重構完一定要跟原版逐行對照「每個副作用都還在嗎？」，有測試的話跑一次測試。漂亮但少一行的程式碼，比醜但正確的程式碼危險多了。
:::

## 結論

可讀性不是什麼玄學，大部分時候就是三件事：**先處理失敗、把重複的抽出來、讓主流程貼著左邊走**。
