## 攔截器：我終於知道它是幹嘛的
從第一篇到這裡，`useApi.ts` 已經活了快一年，但它沒有攔截器。

不是不知道有這個東西。axios 的文件第一頁就有 `interceptors`，我看過。只是一直沒遇到「非用不可」的情境：token 在 `sendRequest` 裡帶、錯誤在 `.then` 裡轉格式，哪裡需要攔截？

直到後端說：token 會過期，過期後回 401 加一個 `status: -99`，你們拿舊 token 去打 `/api/refreshToken` 換新的，然後把原本那個請求再發一次。

這件事沒辦法在 `sendRequest` 裡做。或者說可以做，但你會寫出一個「`sendRequest` 裡面判斷 401 → 呼叫 `refreshToken` → `refreshToken` 裡面又呼叫 `sendRequest`」的遞迴結構，自己都不想看。

攔截器就是為了這種「每個回應都要過一遍，但不該出現在業務邏輯裡」的事情存在的。2024 年 10 月 4 日，醫療後台的 commit「adj：token 交互機制」：
```ts
enum eResponseStatus {
    Requst_Success = 0,
    Requst_Fail = -1,
    Image_Is_Not_Exist = -2,
    File_Is_Not_Exist = -3,
    Token_Expired = -99 // token 過期
}

axios.interceptors.response.use(
    (response) => response,
    async (error) => {
        if (error.response && error.response.status === 401) {
            if (error.response.data.status === eResponseStatus.Token_Expired) {
                if (getToken() !== '') {
                    return refreshToken().then(async (status) => {
                        if (status) {
                            error.config.headers.Authorization = `Bearer ${getToken()}`;
                            return axios.request(error.config); // 重新發送原本的請求
                        }
                    });
                }
            }
            return Promise.reject(error);
        }
        return Promise.reject(error);
    }
);
```
同一個 commit 還做了三件第一次：`iResult` 變泛型 `iResult<T>`、後端狀態碼變 enum、token 的撈取抽成 `getToken()`（順便修掉第二篇那個寫反的 `if`）。

17 天後，供餐系統也加了攔截器。同一個月，兩個專案，兩份幾乎一樣的程式碼。這件事第五篇再算帳。

## 刷新機制的三個洞
那段攔截器看起來很合理：401 → 刷新 → 重送。但它有三個洞，當時一個都沒看到。

### 洞一：沒有鎖
使用者開了一個頁面，頁面一進來同時發三個請求。token 剛好過期，三個都回 401。

三個請求各自進攔截器，各自呼叫 `refreshToken()`，各自去打 `/api/refreshToken`。後端收到三個刷新請求，發三個新 token，前端依序 `setToken`，最後留下來的是第三個。前兩個重送的請求帶的是第一、第二個 token，看後端的實作，有可能已經失效。

正確的做法是一個 Promise 當鎖：第一個 401 觸發刷新，後面的 401 等同一個 Promise，刷完一起重送。這個模式網路上到處都有，我當時沒查，因為沒遇到問題——頁面大部分時候一次只發一個請求。

### 洞二：刷新請求自己也會被攔
```ts
async function refreshToken() {
    return sendRequest('/api/refreshToken', 'POST', {}, {
        Authorization: `Bearer ${getToken()}`
    });
}
```
`refreshToken` 走的是 `sendRequest`，`sendRequest` 走的是 `axios(config)`，`axios` 會過攔截器。如果 `/api/refreshToken` 自己回 401 加 `-99`——例如 refresh token 也過期了——攔截器會再呼叫一次 `refreshToken`。

理論上是無窮遞迴。實際上沒發生，因為 `refreshToken` 的 `.catch` 會 `signOut()`，`getToken()` 變成空字串，第二輪的 `if (getToken() !== '')` 擋住了。靠一個副作用擋遞迴，不是設計，是運氣。

### 洞三：失敗時原請求變成 undefined
```ts
return refreshToken().then(async (status) => {
    if (status) {
        return axios.request(error.config);
    }
    // 沒有 else，沒有 return
});
```
刷新失敗，`status` 是 `false`，`.then` 回傳 `undefined`。攔截器的錯誤處理函式回傳了一個 resolve 成 `undefined` 的 Promise——這代表原本那個請求**成功了**，結果是 `undefined`。

`sendRequest` 的 `.then` 接到 `undefined`，去讀 `axiosResponse.status`，炸。炸了進 `.catch`，`.catch` 去讀 `error.response.data.message`——`error` 是 TypeError，沒有 `response`——又炸。最後頁面看到的是 console 裡兩行紅字，跟一個什麼都沒發生的畫面。

這個洞是後來在供餐系統重現的，使用者閒置太久回來操作，畫面不動也不報錯。查了一陣子才追到這裡。

## 24 天後，刪掉
供餐系統 11 月 5 日加上刷新機制，11 月 29 日的 commit 訊息：

> axios封裝 Adj.3 … 修正成正確的 composables 結構 "刪除 reflash token 機制"

引號是原文就有的，大概是那時候的我也覺得這句需要強調。

✍️ **為什麼刪？** 倉庫裡沒寫。我猜是這樣：供餐系統的後端後來決定不做 refresh token，token 過期就直接登出。上面三個洞裡至少兩個已經在測試時冒出來了，與其補洞，不如趁後端改規格的時候整個拿掉。這段要你確認。

拿掉之後供餐系統的 401 處理變得很簡單：跳一個「登入逾時」的 Dialog，使用者按確定，登出，導回首頁。從 2024 年 12 月到現在都是這樣，再也沒有加回來。

醫療後台沒刪。它的刷新機制活到今天，三個洞也活到今天，因為它的後端一直有 refresh token，而且使用者習慣不會同時開太多東西。

::: tip 兩個專案，同一份程式碼，不同的命運
這件事讓我第一次意識到：封裝的程式碼不是寫完就固定的，它會跟著每個專案的後端、每個專案的使用者習慣，長成不一樣的東西。你以為你在維護一支 `useApi.ts`，其實你在維護三支。
:::

## 攔截器還做了什麼
除了刷新，攔截器在這個階段還接了兩件事。

**400 交給業務層。** 後端的驗證錯誤回 400，axios 預設把非 2xx 當 reject，會進 `.catch` 變成 `null`。但 400 的 body 裡有「哪個欄位錯了」這種資訊，頁面要拿來顯示。所以攔截器把 400 `Promise.resolve(error.response)` 回去，讓它走 `.then` 的路：
```ts
if (error.response.status === 400) { return Promise.resolve(error.response); }
```
這是攔截器第一次被拿來「把錯誤變成不是錯誤」。後來 404、422 也走了這條路。它很好用，但它讓 `sendRequest` 的 `.then` 要同時處理成功跟失敗，職責就混了。這個問題我在[另一個系列](../串%20API%20的那些事/01-axios-封裝-從能用到好用)裡有仔細拆過。

**GET 的參數放 params。** 這個其實跟攔截器無關，但是同一個禮拜改的。原本 `config` 裡一律放 `data`，GET 請求的參數會被 axios 放進 body，後端收不到。改成：
```ts
...(method === 'GET' ? { params: data } : { data })
```
從 2023 年 11 月到 2024 年 11 月，整整一年，這個專案所有的 GET 都是不帶參數的。不是沒有需要帶參數的 GET，是需要的時候都改用 POST 了。醫療後台甚至有一個 commit 叫「全站非GET、POST改為 POST 串接」，把 DELETE 跟 PATCH 全部改成 POST。~~RESTful 是什麼，可以吃嗎。~~

## 這個階段學到的
攔截器是 AOP（切面導向）的概念在前端的落地：有些事情每個請求都要做，但它不該出現在任何一個請求的程式碼裡。token 刷新、全域錯誤提示、loading 狀態，都是這一類。

但攔截器也是最容易藏洞的地方，因為它不在你平常看的路徑上。你寫頁面的時候不會想到攔截器，出問題的時候也不會第一個懷疑它。上面三個洞，每一個都是「寫的時候沒想到，出事的時候找很久」。

下一篇講另一個洞，這個洞是我自己挖的，而且兩個專案都掉進去了：我把攔截器塞進了 composable 函式裡。
