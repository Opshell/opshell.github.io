::: info 這篇的脈絡
CORS、CSRF、XSS 三個縮寫長得很像，常常一起出現在面試題和資安檢測報告裡，也常常被搞混。最常見的情況是：前端看到 console 一片紅的 CORS 錯誤，以為是「被攻擊了」或「要在前端關掉某個安全設定」。
這篇用前端的角度把三者分清楚：它們各自是什麼、誰該負責、前端能做什麼。寫給被 CORS 錯誤折磨過、或被資安報告點名過的前端。
:::

## 懶人包
- **CORS 不是攻擊，也不是防禦**：它是瀏覽器在「同源政策」上開的一道門，錯誤要由**後端**設定回應標頭來解，前端開發時可以用 proxy 繞過。
- **CSRF** 是騙使用者的瀏覽器，帶著他的 cookie 去打你的 API。防法：`SameSite` cookie、CSRF token、改資料的動作不要用 GET。
- **XSS** 是讓攻擊者的程式碼在你的網站上執行。Vue 的 `{{ }}` 會幫你跳脫，危險的是 `v-html` 和使用者給的網址。
- 三者互有關係：用 cookie 存登入狀態要防 CSRF；把 token 放 `localStorage` 不怕 CSRF，但一被 XSS 就整個被偷走。
- 前端能擋的是第一線，真正的把關永遠在後端。

## 技術拆解

### 先講同源政策

瀏覽器有個基本規則：**同源政策（Same-Origin Policy）**。協定、網域、port 三個都一樣才叫同源，不同源的網頁，不能隨便讀對方的資料。

這就像公寓的門禁：住戶可以自由進出，外人要進來，得管理員（後端）點頭。

### CORS：管理員點頭的方式

CORS（Cross-Origin Resource Sharing，跨來源資源共用）就是「管理員點頭」的那套規則。前端在 `https://app.example.com`，要打 `https://api.example.com`，瀏覽器會看 API 的回應有沒有帶 `Access-Control-Allow-Origin`，有允許才把資料交給 JavaScript。

幾個重點：

- **CORS 錯誤是瀏覽器擋的**：簡單請求其實已經送到後端、後端也處理了，只是回應被瀏覽器扣住不給 JavaScript 讀。所以它不是防禦攻擊的機制，而是在同源政策上「放寬」的機制。
- 不是簡單請求（例如帶 `Authorization` 標頭、`Content-Type: application/json`）時，瀏覽器會先送一個 `OPTIONS` 的**預檢請求（preflight）**問能不能送。
- 要帶 cookie 時，後端不能回 `Access-Control-Allow-Origin: *`，必須寫明確的來源，並加上 `Access-Control-Allow-Credentials: true`。
- **解法在後端**。前端能做的只有開發時用 proxy，讓瀏覽器以為是同源。

### CSRF：借刀殺人

CSRF（Cross-Site Request Forgery，跨站請求偽造）利用的是瀏覽器的一個習慣：**送請求到某個網域時，會自動帶上那個網域的 cookie**。

假設使用者登入了你的網站，cookie 還在。他接著打開一個惡意網頁，網頁裡偷偷送一個表單到 `https://your-site.com/api/transfer`，瀏覽器就會乖乖帶上 cookie。對後端來說，這就是使用者本人的請求。

防禦方式：

- **`SameSite` cookie**：設成 `Lax` 或 `Strict`，跨站請求就不會帶 cookie。現在主流瀏覽器沒設定時預設是 `Lax`，但別依賴預設值，明確寫出來。
- **CSRF token**：後端發一個隨機值，前端送請求時放在標頭或表單裡，惡意網頁拿不到這個值。
- **檢查 `Origin` 標頭**：後端確認請求是從自己的網站來的。
- **改資料的動作不要用 GET**：GET 應該是安全、沒有副作用的。

如果你的登入狀態不是放 cookie，而是每次手動在 `Authorization` 標頭帶 token，瀏覽器不會自動帶，CSRF 基本上就打不到你。但是，接下來的 XSS 就要更小心了。

### XSS：在你家裡跑別人的程式

XSS（Cross-Site Scripting，跨站腳本攻擊）是攻擊者想辦法讓他的 JavaScript 在你的網站上執行。一旦成功，他能做的事跟你的前端程式一樣多：讀 `localStorage` 的 token、以使用者身分打 API、改畫面騙使用者輸入密碼。

常見的入口：

- **儲存型**：留言板存了一段 `<img src=x onerror="...">`，每個看留言的人都中招。
- **反射型**：網址參數直接被印到頁面上。
- **DOM 型**：前端程式把使用者輸入塞進 `innerHTML`。

Vue 的好消息是：**模板裡的 `{{ }}` 和屬性綁定都會自動跳脫**，大部分情況你什麼都不用做。要注意的是這幾個破口：

- **`v-html`**：會原樣插入 HTML。內容如果來自使用者，一定要先消毒（例如用 `DOMPurify`）。
- **使用者給的網址**：`<a :href="userUrl">` 的值如果是 `javascript:alert(1)`，點下去就會執行。Vue 不會幫你擋這個，要自己檢查協定。
- **直接操作 DOM**：自己寫 `el.innerHTML = ...` 時，Vue 的保護就不在了。

後端與部署層面還能加兩道保險：

- **CSP（Content Security Policy）**：用回應標頭限制頁面能載入、執行哪些來源的腳本。
- **`HttpOnly` cookie**：JavaScript 讀不到的 cookie，就算被 XSS，token 也偷不走。

## 例子與對比

### 三者比較

| | CORS | CSRF | XSS |
|---|---|---|---|
| 是什麼 | 跨來源讀取的放行規則 | 騙瀏覽器帶 cookie 發請求 | 讓攻擊者的程式在你的網站執行 |
| 是攻擊嗎 | 不是 | 是 | 是 |
| 誰負責 | 後端設定標頭 | 後端為主，前端配合帶 token | 前後端都要 |
| 前端能做的 | 開發時用 proxy | 帶 CSRF token、不用 GET 改資料 | 少用 `v-html`、消毒、檢查網址 |

### 開發時用 Vite proxy 繞過 CORS

```ts
// vite.config.ts
import { defineConfig } from 'vite';

export default defineConfig({
    server: {
        proxy: {
            '/api': {
                target: 'http://localhost:8080', // 後端的位置
                changeOrigin: true
            }
        }
    }
});
```

前端打 `/api/users`，Vite 的開發伺服器幫你轉送到後端，瀏覽器看到的是同源請求。**這只在開發時有效**，上線還是要後端設定 CORS，或用反向代理讓前後端同源。

### 後端該回的標頭（CORS 與 cookie）

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
```

### v-html 一定要消毒

```vue
<script setup lang="ts">
    import DOMPurify from 'dompurify';
    import { computed } from 'vue';

    const props = defineProps<{ html: string }>();

    // 拿掉 <script>、onerror 這類危險的東西，只留下安全的 HTML
    const safeHtml = computed(() => DOMPurify.sanitize(props.html));
</script>

<template>
    <div class="article-body" v-html="safeHtml" />
</template>
```

### 使用者給的網址要檢查協定

```ts
/** 只允許 http／https，其他（例如 javascript:）一律換成 # */
export function toSafeUrl(url: string): string {
    try {
        const parsed = new URL(url, window.location.origin);
        return ['http:', 'https:'].includes(parsed.protocol) ? parsed.href : '#';
    } catch {
        return '#';
    }
}
```

```vue
<a :href="toSafeUrl(user.website)" target="_blank" rel="noopener noreferrer">個人網站</a>
```

### CSP 標頭範例

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'
```

只允許載入自己網域的腳本，被注入的 inline script 就跑不起來。實際要開放哪些來源，依專案用到的第三方服務調整。

## 結論

三個縮寫一次記：**CORS 是門禁規則、CSRF 是借刀殺人、XSS 是在你家跑別人的程式**。
看到 CORS 錯誤，先別急著在前端找開關，那是後端的設定；寫 `v-html` 和綁使用者給的網址時，多想一秒「這是誰給的資料」。前端是第一線，但別忘了真正的保全永遠在後端。~~所以 CORS 錯誤請直接截圖丟給後端，這不是甩鍋，這是分工。~~
