## 懶人包
- 命名卡關很常見，那是你正在建立自己的程式碼風格、命名風格的過程。
- 給自己一套規則，漸漸的這種情況就會越來越少；找到自己和團隊都能接受、大家都看得懂的寫法最重要。
- 寫多了之後會發現：**看得懂，比炫技更重要**。
- 寫的時候加點註解、邏輯理順、型別乖乖處理、不要用縮寫，就能大幅降低「過幾天看不懂」的問題。
- 回頭看覺得自己寫得跟大便一樣，代表你一直在進步。

## 觀點拆解

### 命名卡關，很正常
蠻常見的。取名字這件事，連資深工程師都會卡，`Phil Karlton` 那句「電腦科學只有兩件難事：快取失效和命名」不是講好玩的。

請 AI 幫忙取名也沒什麼不好，它就像一本會說話的字典。問題不在於用不用工具，而在於你**有沒有一套自己的規則**來判斷它給的名字好不好。沒有規則的話，就會陷入「這個好像不錯，那個好像也可以」的無限迴圈。

總會漸漸找到自己的、團隊的程式碼風格和命名風格。給自己一個規則，漸漸的這個情況就會越來越少。現在你經歷的，算是建立風格的過程。

### 團隊也是問題
找到自己和團隊都可以接受、大家都看得懂的寫法最重要。

但團隊也是問題：不是每個人都能 Get 到你的體認，需要溝通。也有那種有程式碼潔癖的人，會覺得「這段為什麼不抽成共用？」。所以寫多了之後，我開始覺得：

**看得懂，比炫技更重要。**

一段程式碼寫一次，但會被讀很多次：Code Review 讀一次、修 Bug 讀一次、新人接手再讀一次。寫的人多花五分鐘，讀的人就省下五十分鐘。

### 過幾天就看不懂，怎麼辦
與其事後整理，不如寫的當下就降低未來看不懂的機率。我的習慣是：

1. 寫的時候加點註解，尤其是「為什麼這樣做」。
2. 思考邏輯理順一點，先想清楚再動手。
3. `TypeScript` 的型別乖乖處理，不要懶。
4. 變數、函式盡量不要用縮寫。
5. 盡量拉高可讀性，不要為了炫技搞得很複雜。

這幾點做到，可以很大部分降低你遇到的問題。

### 覺得自己寫得像大便？恭喜
然後，過幾天回頭看自己的程式碼，覺得自己弄得跟大便一樣，這是很正常的，代表你一直在進步。

就像翻到國中寫的日記，會尷尬到想把它燒掉，不是因為當時的你很爛，而是現在的你長大了。

前提是：有按照自己、團隊的風格穩穩地發揮。如果每次回頭看都是「完全不同風格的大便」，那就不是進步，是還沒找到風格 ~~（那就再回去看第一段）~~。

## 例子與對比

### 縮寫與炫技 vs 看得懂
```ts
interface User {
    name: string;
    email: string;
    isActive: boolean;
    isDeleted: boolean;
}

// 炫技版：短、潮，但三天後連自己都要停下來想
const fmt = (u: User[]) => u.filter(({ isActive: a, isDeleted: d }) => a && !d).map(({ name: n, email: e }) => `${n}<${e}>`).join(', ');

// 看得懂版：長一點，但讀一次就懂
function formatActiveUserContacts(users: User[]): string {
    const activeUsers = users.filter((user) => user.isActive && !user.isDeleted);

    return activeUsers
        .map((user) => `${user.name}<${user.email}>`)
        .join(', ');
}
```

### 給自己的命名規則範例
有規則之後，取名就從「靈感」變成「套公式」：

| 類型 | 規則 | 例子 |
| :--- | :--- | :--- |
| 布林值 | `is`、`has`、`can`、`should` 開頭 | `isLoading`、`hasPermission` |
| 函式 | 動詞開頭 | `fetchUsers`、`formatPrice` |
| 事件處理 | `handle` + 事件 | `handleSubmit`、`handleRowClick` |
| 陣列 | 複數名詞 | `users`、`orderItems` |
| 常數 | 全大寫底線 | `MAX_RETRY_COUNT` |
| 註解 | 寫「為什麼」，不寫「做什麼」 | `// 後端分頁從 0 開始，所以要減 1` |

規則本身不用完美，重點是**一致**。團隊一起訂、寫進文件、交給 `ESLint` 檢查，比每個人各自追求完美有用得多。

## 結論
命名卡關、過幾天看不懂、回頭看覺得是大便，這三件事每個工程師都經歷過。給自己一套規則、跟團隊對齊、把可讀性擺在炫技前面，這些問題就會慢慢變少。

程式碼是寫給人看的，順便讓電腦執行而已。
