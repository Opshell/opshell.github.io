::: info 這篇的脈絡
「不要重複造輪子」幾乎是工程師的口頭禪，但另一派人會說「不自己造過，永遠不懂輪子怎麼轉」。兩邊都有道理，常見的情況是：有人花兩週自己寫了一個日期處理工具，結果時區一換就全壞；也有人什麼都裝套件，`node_modules` 比專案本身大一百倍。這篇是我對「造輪子」這件事的看法。
:::

## 懶人包
- 我相信真的有造輪子的需求，造輪子本身不是原罪。
- 但在動手之前，**請先閱讀過別人的輪子，看懂這些開源大神做了什麼**，真的了解過再重新造。
- 讀懂之後，通常會發生兩件事之一：發現別人的輪子其實夠用，或是知道自己的輪子要做得哪裡不一樣。
- 學習用的輪子盡量造；要上線、要給團隊用的輪子，請先算過維護成本。

## 觀點拆解

### 造輪子不是原罪
我也相信真的有造輪子的需求。常見的理由有這幾種：

1. **現有的輪子太大**：只需要一個函式，卻要裝一整包套件。
2. **現有的輪子不合用**：需求很特殊，用套件要繞一大圈。
3. **想學會它**：自己寫一次 `debounce`、一次簡易版的響應式系統，比讀十篇文章都有用。
4. **輪子沒人顧了**：套件三年沒更新，issue 堆成山。

這些都是正當理由。問題不在造不造，而在於**造之前有沒有先看過別人怎麼造**。

### 先讀別人的輪子
所以我會建議：「請先閱讀過別人的輪子，看懂這些開源大神做了什麼」，真的了解過再重新造輪子。

這就像想自己開一家拉麵店，總要先去吃過幾家名店吧？吃過之後你才知道湯頭要熬多久、麵條要多粗，也才知道自己的店要賣什麼不一樣的東西。沒吃過就開店，很容易端出一碗「自己覺得好吃」的泡麵。

讀別人的原始碼，最常見的收穫是看到那些**你想不到的邊界情況**：

- 日期處理：時區、夏令時間、閏年、不同語系的格式。
- 深拷貝：循環引用、`Date`、`Map`、`Set`、`RegExp`。
- 防抖節流：`leading`、`trailing`、取消、`this` 綁定。

這些東西不讀，自己寫的版本跑 Demo 都會過，上線之後才一個一個爆出來。

### 讀懂之後的兩種結局
1. **發現別人的輪子其實夠用**：恭喜，省下好幾天。而且你現在知道它怎麼運作，出問題時也知道從哪裡下手。
2. **知道自己的輪子要哪裡不一樣**：這時候造出來的輪子才有存在的理由，而且會站在巨人的肩膀上，不用從石器時代開始磨。

### 學習的輪子 vs 上線的輪子
自己練習造的輪子，壞了只有自己痛；放進團隊專案的輪子，壞了是全團隊一起痛，而且你離職之後，還會有人在背後默默念你的名字 ~~（不是好的那種念法）~~。

要上線的輪子，請多問自己幾題：
- 有沒有測試？
- 有沒有文件？
- 誰負責維護？
- 換成現成套件的話，要花多少時間？

## 例子與對比

以「深拷貝」這個經典的輪子為例：

```ts
// 自己隨手造的版本：Demo 會過
function deepClone<T>(value: T): T {
    return JSON.parse(JSON.stringify(value));
}

const source = { createdAt: new Date(), tags: new Set(['vue']) };
const copied = deepClone(source);
// createdAt 變成字串、tags 變成空物件，而且遇到循環引用直接報錯
```

讀過別人的輪子（或規格）之後，你會知道瀏覽器和 Node 早就內建了 `structuredClone`，`Date`、`Map`、`Set`、循環引用都處理好了：

```ts
const source = { createdAt: new Date(), tags: new Set(['vue']) };
const copied = structuredClone(source);

console.log(copied.createdAt instanceof Date); // true
console.log(copied.tags.has('vue')); // true
```

| | 直接造 | 先讀再造 |
| :--- | :--- | :--- |
| 開發速度 | 一開始快 | 一開始慢 |
| 邊界情況 | 上線後才發現 | 動手前就知道 |
| 結果 | 常常是比較差的複製品 | 用現成的，或做出真正不一樣的東西 |
| 自己的成長 | 學到一點 | 學到很多 |

## 結論
造輪子沒問題，閉著眼睛造輪子才有問題。先讀懂別人的輪子，你可能會發現不用造了；就算還是要造，也會造得更圓。

畢竟，輪子這東西，方的轉起來真的很累。
