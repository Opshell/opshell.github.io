::: info 這篇的脈絡
前後端分離之後，前端不再是「套版」，而是一個獨立的應用程式；後端也不再吐 HTML，只負責 API。分工變清楚了，新的問題也跟著來：前端等後端的 API，後端等前端說要什麼欄位；好不容易接上，才發現日期格式、欄位命名、錯誤怎麼回都對不上。
這篇整理一套常見的協作流程，寫給剛開始前後端分離、或已經分離但每次對接都很痛的團隊。
:::

## 懶人包
- 前後端分離最大的成本不是技術，是**互相等待**和**格式對不上**。
- **先訂 API 規格，再寫程式**：規格是兩邊共同的合約，最好只有一份，而且由一方負責維護。
- **用 mock 平行開發**：規格訂好，前端就能用假資料先做，不用等後端。
- **統一回應與錯誤格式**：成功長什麼樣、失敗長什麼樣、錯誤訊息給誰看，先講好。
- **規格要改，先改文件再改程式**，並通知另一邊；口頭說好的改動，三天後一定有人忘記。

## 觀點拆解

### 痛點：兩個人在搭同一座橋

前後端分離就像兩隊人從河的兩岸往中間搭橋。如果一開始沒對好位置和高度，在中間碰頭時才發現差了半公尺，就只能拆掉重搭。
API 就是橋中間接合的那個點。協作的重點，是在動工前把接合點的規格講清楚。

### 1. 規格先行：一份合約，一個負責人

需求確定之後，第一件事不是寫程式，而是前後端一起訂 API 規格：

- 路徑與方法：`GET /api/products`、`PUT /api/products/:id`
- 請求參數：哪些必填、型別、格式（日期是 ISO 8601 還是 timestamp？）
- 回應格式：成功時的資料結構、分頁資訊放哪
- 錯誤：有哪些錯誤碼、各代表什麼

規格要**寫下來**，而且**只有一份**。常見的選擇是 OpenAPI（Swagger）文件，或一份大家都看得到的 Markdown。重點是決定**誰負責改它**：通常是後端，因為實作在後端；前端有需求就提出，由負責人更新。
兩邊各抄一份規格，是對不上的開始。

### 2. 用 mock 平行開發

規格訂好之後，前端不用等後端寫完，直接照規格做假資料開始開發：

- 後端或測試工具提供 mock server（例如 Postman 的 Mock Server）。
- 前端自己在瀏覽器裡攔截請求回假資料（例如 `MSW`）。

這樣兩邊可以同時開工，最後只要把 mock 換成真的 API。規格訂得越清楚，最後接上時的驚喜就越少。

### 3. 統一回應與錯誤格式

每支 API 都長得不一樣，是前端封裝 API 時最痛的事。先講好全專案通用的格式：

- 成功的資料包在哪一層、分頁資訊放哪。
- 失敗時用 HTTP 狀態碼表達大分類（400 參數錯、401 沒登入、403 沒權限、404 找不到、500 伺服器錯），內容再帶細節。
- 錯誤訊息是**給使用者看的**還是**給工程師看的**？給使用者看的就直接顯示，前端不用再翻譯一次。
- 欄位命名：後端習慣 snake_case、前端習慣 camelCase，誰負責轉換？

### 4. 誰負責什麼，邊界要清楚

有些事情兩邊都能做，就更要講清楚：

| 事情 | 常見的分工 |
|---|---|
| 資料驗證 | 前端驗證是為了體驗，後端驗證是為了安全，**兩邊都要做** |
| 權限 | 前端依權限決定畫面，後端決定能不能真的存取 |
| 排序、分頁、篩選 | 資料量大就交給後端，前端只送條件 |
| 新增、修改後的最新資料 | 回應直接帶回新資料，或前端另外重抓，二選一講好 |
| 日期時區 | 傳輸一律用 UTC 的 ISO 8601，顯示時前端再轉 |

### 5. 變更流程：先改文件，再改程式

開發中規格一定會改，這很正常。問題是改了沒講。
規則很簡單：**要改 API，先改規格文件，通知另一邊，再改程式**。能在 PR 裡附上規格的變更最好，review 的人一眼就知道影響範圍。

## 例子與對比

### 用 OpenAPI 寫下合約

```yaml
# openapi.yaml（節錄）
openapi: 3.1.0
info:
  title: Product API
  version: 1.0.0
paths:
  /api/products:
    get:
      summary: 取得產品列表
      parameters:
        - name: page
          in: query
          schema: { type: integer, minimum: 1 }
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                type: object
                properties:
                  items:
                    type: array
                    items: { $ref: '#/components/schemas/Product' }
                  total: { type: integer }
components:
  schemas:
    Product:
      type: object
      required: [id, title]
      properties:
        id: { type: integer }
        title: { type: string }
```

有了 OpenAPI 文件，前端還能直接產生型別，不用手抄：

```sh
npx openapi-typescript ./openapi.yaml -o ./src/types/api.d.ts
```

### 前端用 MSW 先做假資料

```ts
// src/mocks/handlers.ts
import { http, HttpResponse } from 'msw';

export const handlers = [
    http.get('/api/products', () => {
        return HttpResponse.json({
            items: [
                { id: 1, title: '測試產品 A' },
                { id: 2, title: '測試產品 B' }
            ],
            total: 2
        });
    })
];
```

`MSW` 在瀏覽器裡用 Service Worker 攔截請求，前端程式碼完全照打真的 API 的方式寫。後端好了，關掉 mock 就接上。實際的啟動設定以官方文件為準。

### 統一的錯誤格式

```json
{
    "error": "這個產品名稱已經有人用了",
    "code": "PRODUCT_TITLE_DUPLICATED",
    "fields": {
        "title": ["名稱重複"]
    }
}
```

`error` 給使用者看、`code` 給程式判斷、`fields` 給表單標紅，三種用途分開，前端就不用猜。

### 協作流程：沒有規格 vs 規格先行

| | 沒有規格，邊做邊問 | 規格先行 |
|---|---|---|
| 開工時間 | 前端等後端 API 好了才開始 | 兩邊同時開始 |
| 對接 | 接上才發現格式不對 | 只要把 mock 換掉 |
| 規格變更 | 口頭說、聊天室說，各自記 | 改文件、通知、改程式 |
| 新人加入 | 問人 | 看文件 |

## 結論

前後端分離不是把工作切成兩半各做各的，而是**先把接合點講清楚，才能放心各做各的**。一份大家都認的規格、一套 mock、一個統一的格式、一條「先改文件」的規則，就能省下大部分的來回。
橋要從兩岸一起搭，接合點就要先畫好。~~不然最後在河中間對看，只能比誰的嗓門大。~~
