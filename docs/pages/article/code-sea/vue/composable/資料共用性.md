我收到一個關於 composable 的 `ref` 狀態問題：兩個頁面用到同一個 composable 裡的 `ref`，A 頁面改了狀態，B 頁面會看到改變後的值嗎？他聽到兩種說法，自己試是不會變，對方截圖給他看卻變了，不知道哪個才對。

看了兩邊的原始碼才知道，兩個人把 `ref` 放在不同的地方，根本沒有一致做法。這種細節很多人沒注意，所以整理一下，寫給剛開始寫 composable 的人。
:::

## 懶人包
- 先講答案：-|看你的 `ref` 是不是在 export 的那個函式裡面定義的|-。
- 寫在函式**裡面**：每次呼叫都重新建立一份，各頁面各自一份，不會互相污染。
- 寫在函式**外面**（模組頂層）：整個 App 只有一份，A 頁改了，切到 B 頁就會看到。
- 這不是 Vue 的魔法，是 ES Module 的特性：模組只會被執行一次，頂層變數就是單例。
- 要共享就刻意共享（Pinia 或 VueUse 的 `createGlobalState`），不必共享的一律放進函式裡。

## 技術拆解

### composable 只是一個函式
composable 沒有什麼特別的身分，它就是一個「會用到 Vue 響應式 API 的函式」。函式每被呼叫一次，裡面的程式碼就跑一次，`ref()` 也就建立一份新的。

所以 `useStateRef()` 在 A 頁面呼叫一次、B 頁面呼叫一次，拿到的是兩個不同的 `state`，誰改都不會影響對方。這也是為什麼「現在改了資料，跳到下一頁不會看到被改過的結果」。

### 模組頂層只會跑一次
寫在函式外面的那行 `const sharedState = ref({})`，是在**這個模組第一次被 import 的時候**執行的。之後不管被 import 幾次，拿到的都是同一個模組實例，也就是同一個 `sharedState`。

它只是寫在外頭、被 return 出去，完全參與不到 `useStateRef()` 的初始化。所以：

- `state` 怎樣都不會被共享。
- `sharedState` 被拿來寫入就會互相影響：資料變了，另一頁也在用同一個物件，切換路由就會看到。

### 這跟 Vue 沒有直接關係
群組裡有大大補充得很好：放外面可以共享狀態，跟 Vue 沒有直接關係，那是 JS ES Module 本身的特性，CommonJS 也一樣（`require` 也會快取模組）。

同一個特性還有個常見的副作用：`<script type="module">` 裡宣告的函式不會掛到 `window`，所以 HTML 上直接寫 `onclick="doSomething()"` 會找不到函式，事件傳不到，要改用 `addEventListener` 綁。模組有自己的作用域，這是同一件事的兩面。

也有人提到，補一點 runtime 相關的知識（模組怎麼載入、作用域怎麼形成）就能自己釐清這類問題。AI 回答這種問題很方便，但新手往往不知道該怎麼問，因為他根本沒意識到問題出在「寫在哪一行」。

### SSR 要特別小心
如果專案有 SSR（例如 Nuxt），模組頂層的狀態在伺服器上是**所有請求共用**的，A 使用者的資料可能被 B 使用者看到。這種情況請用框架提供的狀態工具（例如 Nuxt 的 `useState`）或 Pinia，不要自己在模組頂層放 `ref`。

### 旁支：watch 什麼時候執行
討論中也有人提到 composable 本身就能當 state 用，還可以搭配 `watch` 做狀態連動。這裡補一個容易誤會的點：`watch` 預設的 `flush` 是 `'pre'`，回呼會被排進佇列、在元件更新前批次執行，**不是**改值的當下同步觸發；真的需要同步執行要明確寫 `flush: 'sync'`，而且要小心效能。細節以官方文件為準。

## 例子與對比

### 函式內 vs 函式外
```ts
// composables/useStateRef.ts
import { ref } from 'vue';

// 模組頂層：整個 App 共用一份
const sharedState = ref<{ keyword: string }>({ keyword: '' });

export const useStateRef = () => {
    // 函式內：每次呼叫都是新的一份
    const state = ref<{ keyword: string }>({ keyword: '' });

    return {
        state,
        sharedState
    };
};
```

```vue
<!-- PageA.vue -->
<script setup lang="ts">
import { useStateRef } from '@/composables/useStateRef';

const { state, sharedState } = useStateRef();
state.value.keyword = 'A 的關鍵字';
sharedState.value.keyword = 'A 寫進共用區';
</script>
```

```vue
<!-- PageB.vue -->
<script setup lang="ts">
import { useStateRef } from '@/composables/useStateRef';

const { state, sharedState } = useStateRef();
console.log(state.value.keyword); // ''，自己的一份
console.log(sharedState.value.keyword); // 'A 寫進共用區'，從 A 跳過來就看得到
</script>
```

| 寫在哪 | 建立時機 | 幾份 | 適合 |
|---|---|---|---|
| 函式裡面 | 每次呼叫 | 每個呼叫者一份 | 表單狀態、載入狀態、頁面自己的資料 |
| 模組頂層 | 第一次 import | 整個 App 一份 | 刻意要共享的全域狀態 |

### 要共享，就刻意共享
如果真的要共享，與其讓同事看不出來，不如明講：

```ts
// composables/useSearchState.ts
import { createGlobalState } from '@vueuse/core';
import { ref } from 'vue';

// 名字和工具都在告訴讀的人：這是全域共享的
export const useSearchState = createGlobalState(() => {
    const keyword = ref('');

    return { keyword };
});
```

狀態再複雜一點、需要 devtools 追蹤或 SSR，就交給 Pinia。相關的功能但不必共享的，還是放進函式裡。

## 結論
同一個 composable 會不會互相污染，不是玄學，是那一行 `ref` 寫在函式的裡面還是外面。

這讓我想到：看到別人用 lodash 的 `_.forEach` 而不是原生 `forEach`，第一反應可能是覺得很芭樂，但也許人家是為了提前中斷迴圈（`return false`）、或回傳新的集合才這樣用，那就沒問題。-|深入理解一個工具，才會知道差別是什麼|-，ref 要放哪裡也是一樣的道理。
