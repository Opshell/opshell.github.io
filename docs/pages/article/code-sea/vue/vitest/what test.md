開始研究前端測試之後，一定會撞到 TDD（Test Driven Development，測試驅動開發）：先寫測試、再寫程式、最後重構。理論上很美，但看國外論壇的討論，TDD 目前其實不太被推崇，現在比較推的是 BDD（Behavior Driven Development，行為驅動開發）。

在群組聊到這件事，大家的反應很一致。這篇整理那串吐槽，寫給正在猶豫「要不要照書上的 TDD 來」的人。參考：[TDD for frontend engineers](https://codedrivendevelopment.com/posts/tdd-for-frontend-engineers)。延伸：[為什麼要寫測試](./why%20testing)、[在 Vue + Vite 專案裝好 Vitest](./vitest)。
:::

## 懶人包
- TDD 的前提是-|需求要先定義清楚|-，需求一直變的團隊，測試會一直被打掉重寫。
- BDD 從「使用者看到什麼、做了什麼」出發寫測試，比較貼近需求，也比較不怕實作細節改動。
- 寫測試 OK，但沒有 QA、沒有時間的情況下，不可能要求 RD 把整個專案都測完，涵蓋率保證不了。
- 實際一點的做法：挑最容易壞、最不能壞的地方先測，用行為的角度寫。

## 觀點拆解

### TDD 卡在哪：需求不清楚
群組裡伊莉莎白大說得很直接：「我自己也沒很喜歡 TDD，因為遇到的團隊根本不會幫你把需求定義清楚 www」，結果就變成這樣的循環：

```txt
測試寫完 -> 開發 -> 打掉 -> 測試寫完 -> 開發 -> 打掉 -> ...
```

TDD 要你先寫測試，等於先把「正確的行為長什麼樣」寫死。需求清楚的時候，這是很好的規格；需求不清楚的時候，你寫的就是一份很快會作廢的規格。

### 在台灣的現實
我第一次聽到 TDD 的時候，就覺得在台灣完全不適用……光寫測試就寫死你。常見的開發流程比較像這樣：

```txt
開發 > 測試 > 開發 > 更改需求 > 開發 > 更改需求 > 測試 > 更改需求 > 更改需求 > 更改需求 > 打掉重來 > 刪庫跑路
```

~~（最後一步請勿模仿。）~~

這不是說 TDD 不好，而是它對環境有要求：需求要穩、時程要留給測試、團隊要有共識。三個缺一個，TDD 就會變成額外的負擔。

### 沒有 QA，涵蓋率保證不了
另一個現實是：寫測試 OK，但在沒有 QA 的情況下，寫測試無法保證測試涵蓋率。RD 的時間就那麼多，也無法要求 RD 把整個專案都測完。

所以問題從「要不要 TDD」，變成「時間有限，測試要花在哪裡」。

### BDD 為什麼比較被接受
BDD 的重點不是「先寫測試」，而是-|用行為描述來寫測試|-：

- 用「假設（Given）…當（When）…那麼（Then）…」的句型描述需求，PM、QA、RD 都看得懂。
- 測的是使用者看得到的結果（畫面上出現什麼、按下去發生什麼），不是內部用了哪個變數。
- 實作怎麼改都沒關係，只要行為沒變，測試就不用動。

需求改了，改的是那一句行為描述；比起 TDD 一改需求就得連帶重寫一堆針對實作的測試，BDD 在需求常變的環境裡活得比較久。

## 例子與對比

### 針對實作 vs 針對行為
同一個「購物車數量加一」的需求，兩種寫法：

```ts
// 針對實作：元件內部改名、改寫法，測試就壞
it('呼叫 increase 後 count 變成 2', () => {
    const wrapper = mount(CartItem, { props: { quantity: 1 } });

    (wrapper.vm as any).increase();

    expect((wrapper.vm as any).count).toBe(2);
});
```

```ts
// 針對行為：只要使用者看到的結果一樣，測試就不用改
describe('購物車項目', () => {
    describe('假設數量是 1', () => {
        it('當使用者按下「＋」，畫面上的數量變成 2', async () => {
            const wrapper = mount(CartItem, { props: { quantity: 1 } });

            await wrapper.get('[data-test="increase"]').trigger('click');

            expect(wrapper.get('[data-test="quantity"]').text()).toBe('2');
        });
    });
});
```

### 三種做法比較

| | TDD | BDD | 事後補測試 |
|---|---|---|---|
| 什麼時候寫 | 寫程式之前 | 需求確定時，可前可後 | 功能做完之後 |
| 測的對象 | 函式、單元 | 使用者行為 | 看人 |
| 需求常改時 | 一直打掉重寫 | 改行為描述就好 | 容易被跳過 |
| 前提 | 需求清楚、時間足夠 | 對「行為」有共識 | 要有紀律 |

### 時間有限時，先測哪裡
- 金額計算、權限判斷這種-|壞了會出大事|-的純函式邏輯。
- 每次改版都容易被改壞的共用元件、共用 composable。
- 修過的 bug：修完補一支測試，確保它不會回來。

## 結論
TDD 不是不好，是它挑環境。需求穩定、時程寬裕的團隊，它是很棒的紀律；需求一天三變的地方，先從 BDD 的角度、挑最痛的地方寫起，比較實際。

測試是保險，不是信仰，買得起多少就先保多少。
