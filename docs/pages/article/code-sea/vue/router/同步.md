::: info 這篇的脈絡
列表頁的 `getList` 幾乎每個後台專案都有：讀路由上的頁碼、組網址、打 API、塞資料、關 loading。常見的情況是同一個專案裡，有人用 `new Promise` 手動包一層，有人用 `async`，還有人 `await` 後面接 `.then()`。這篇把兩種寫法擺在一起比，再整理成我現在會用的版本。寫給對 Promise 還有點模糊的人。
:::

## 懶人包
- `getData` 本來就回傳 Promise，再用 `new Promise` 包一層是多餘的（俗稱 Promise 建構子反模式）。
- `async` 函式本身就回傳 Promise，`return` 是 resolve、`throw` 是 reject。
- `await` 後面接 `.then().catch()` 可以跑，但兩種風格混在一起不好讀，挑一種就好。
- `catch` 了卻不往外丟，呼叫的人就永遠不知道失敗了。
- 頁碼要在函式**裡面**讀，每次呼叫才會拿到最新的。

## 技術拆解

### A 寫法：new Promise
```ts
const getList = () => {
    // 請求的頁面 (放裡面才會每次都改) // 放外面會卡死
    const currentPage = route.params?.page || 1;

    const url = `/api/member/list?page=${currentPage}&keyword=${keyword.value}`;
    return new Promise((resolve, reject) => {
        getData(url) // 本機測試環境
            .then((res) => {
                elStatusStore.endLoading();

                setTimeout(() => {
                    memberList.value = res?.data || [];

                    lastPage.value = res?.paginator?.last_page || 10;
                }, 200);
                resolve(res);
            }).catch((error) => {
                console.error(error);
                elStatusStore.endLoading();
                reject(error);
            });
    });
};
```

優點：錯誤有 `reject` 出去，呼叫的人可以接。
問題：`getData` 已經是 Promise 了，外面再包一層只是在「把 Promise 轉手一次」。手動包的時候只要漏寫一個 `resolve` 或 `reject`，這個 Promise 就永遠不會結束。`endLoading` 也在兩個地方各寫一次。

### B 寫法：async
```ts
const getList = async () => {
    // 請求的頁面 (放裡面才會每次都改) // 放外面會卡死
    const currentPage = route.params?.page || 1;

    const url = `/api/member/list?page=${currentPage}&keyword=${keyword.value}`;
    await getData(url) // 本機測試環境
        .then((res) => {
            setTimeout(() => {
                memberList.value = res?.data || [];

                lastPage.value = res?.paginator?.last_page || 10;
            }, 200);
        }).catch((error) => {
            console.error(error);
        });

    elStatusStore.endLoading();
};
```

優點：短很多，`endLoading` 只寫一次。
問題：`.catch` 把錯誤吞掉了，`getList()` 永遠成功，呼叫的人不知道失敗；`await` 和 `.then` 混用，讀的時候要在兩種思路間切換。

### 「放裡面才會每次都改」
這個註解很重要。`currentPage` 如果寫在函式外面，只會在元件建立時讀一次，之後換頁也還是第一頁。放在函式裡，每次呼叫都重新讀 `route.params`。這跟 composable 的 ref 寫在函式裡外是同一個道理。

### 那個 setTimeout 200
兩個版本都延遲 200ms 才塞資料，常見的原因是想配合 loading 動畫或過場。但這會讓 `getList()` 結束時資料其實還沒進來，呼叫的人如果接著做事（例如捲到頂端、算筆數）會拿到舊資料。要配合動畫，比較好的做法是讓動畫等資料，而不是讓資料等動畫，例如用 `<Transition>` 處理進場。

## 例子與對比

### C 寫法：純 async/await + try/finally
```ts
const getList = async () => {
    // 放在函式裡，每次呼叫都讀最新的頁碼
    const currentPage = Number(route.params?.page) || 1;
    const url = `/api/member/list?page=${currentPage}&keyword=${encodeURIComponent(keyword.value)}`;

    try {
        const res = await getData(url);
        memberList.value = res?.data ?? [];
        lastPage.value = res?.paginator?.last_page ?? 1;

        return res;
    } catch (error) {
        console.error('取得列表失敗', error);
        throw error; // 讓呼叫的人知道失敗了
    } finally {
        elStatusStore.endLoading(); // 成功失敗都會關
    }
};
```

- `finally` 讓 `endLoading` 只寫一次，而且不會漏。
- `throw error` 把錯誤交給呼叫的人決定要不要提示使用者。
- `encodeURIComponent` 避免關鍵字有 `&`、`#` 時網址壞掉。
- `lastPage` 的預設值改成 `1`，原本的 `10` 會在 API 沒回分頁時，顯示出 10 頁不存在的頁碼。

| | A：new Promise | B：async + .then | C：async + try/finally |
|---|---|---|---|
| 程式碼長度 | 長 | 短 | 中 |
| 錯誤傳得出去 | 可以 | 被吞掉 | 可以 |
| loading 關閉 | 寫兩次 | 寫一次 | `finally` 保證 |
| 風格 | callback 包 Promise | 混用 | 一致 |
| 漏寫 resolve 的風險 | 有 | 無 | 無 |

## 結論
`new Promise` 是拿來把「不是 Promise 的東西」（例如舊式 callback API、`setTimeout`）包成 Promise 的，不是拿來包已經是 Promise 的東西。手上已經有 Promise，就 `await` 它；要收尾就 `finally`；要讓別人知道失敗就 `throw`。

三個關鍵字，換掉一整層包裝紙。
