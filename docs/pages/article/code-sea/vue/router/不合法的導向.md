::: info 這篇的脈絡
在 Vue Router 的 `beforeEnter` 裡，有時候要先做一些驗證，驗證失敗就導去別的地方。常見的例子是會員詳細頁：網址上有 `member_id`，進頁面前先確認 store 裡有沒有這個會員，沒有就打 API 拿，拿不到就導回會員列表。寫起來很直覺，結果 console 噴了一個看不太懂的錯誤。這篇把三種寫法和排查方向整理起來，寫給在路由守衛裡處理非同步驗證的人。
:::

## 懶人包
- 路由守衛可以 `return` 一個路由位置來導向，`return false` 取消導航，什麼都不回就放行。
- 從 `try/catch` 的 `catch` 裡 `return` 導向，在 JS 裡是合法的，三種寫法的結果應該一樣。
- 真正要小心的是：**在 try 裡打錯變數名，也會被 catch 接住**，結果每次都被導回列表，看起來像 API 失敗。
- `Navigation aborted ... via a navigation guard` 代表導航被某個守衛中斷，要往「導向的目標」和「其他守衛」去查。
- 我比較推薦「先拿結果、再決定導向」的旗標寫法：守衛的出口集中在最後，好讀也好除錯。

## 技術拆解

### 守衛的回傳值
Vue Router 4 的守衛不用再呼叫 `next()`，直接用回傳值決定：

| 回傳 | 結果 |
|---|---|
| `undefined`／`true` | 放行 |
| `false` | 取消這次導航 |
| 路由位置（`{ name: 'MemberList' }`） | 中斷這次，改導到新位置 |
| 丟出錯誤 | 導航失敗，錯誤會往外拋 |

`async` 守衛也一樣，回傳的 Promise resolve 什麼就照什麼處理。

### 第一種：try/catch 裡直接 return
```ts
beforeEnter: async (to) => {
    const memberStore = piniaStore.useMemberStore;
    const { memberState } = storeToRefs(memberStore);

    const memberId = Number(to.params?.member_id) || 0;
    // [-]沒選定會員就去導向會員列表
    if (!memberId) {
        return { name: 'MemberList', params: { page: 1 } };
    }

    // [-]當前會員資料同這個會員的時候 直接導向
    if (memberState.value.member_id === memberId) { return; }

    // [-]上述條件不符合時重新取得會員資料
    try {
        const result = await sendRequest(`/api/present_pat/simpledata/${MemberId}`);
        if (!result?.status) { throw new Error('取得病患資料失敗'); }

        MemberStore.updateMember(result.data);
    } catch (_error) {
        return { name: 'MemberList', params: { page: 1 } };
    }
};
```

然後它噴錯誤了：

```
vue-router.mjs:962  Uncaught (in promise) Error: Navigation aborted from "/" to "/Member-list/1" via a navigation guard.
```

仔細看 `try` 裡面：用的是 `MemberId` 和 `MemberStore`（大寫開頭），但上面宣告的是 `memberId` 和 `memberStore`。這會丟出 `ReferenceError`，而它**也被 catch 接住了**，所以不管 API 正不正常，每次都會被導回列表。`catch (_error)` 又把錯誤吞掉，console 什麼都看不到。

-|try/catch 不只接 API 的錯，連你自己的錯字也一起接|-，這是它最陰險的地方。

### 第二種：.then().catch() 把結果變成值
```ts
beforeEnter: async (to) => {
    const memberStore = piniaStore.useMemberStore;
    const { memberState } = storeToRefs(memberStore);

    const memberId = Number(to.params?.member_id) || 0;
    // [-]沒選定會員就去導向會員列表
    if (!memberId) {
        return { name: 'MemberList', params: { page: 1 } };
    }

    // [-]當前會員資料同這個會員的時候 直接導向
    if (memberState.value.member_id === memberId) { return; }

    // [-]上述條件不符合時重新取得會員資料
    const newMemberFlag = await sendRequest(`/api/mamber/${memberId}`).then((res) => {
        if (!res?.status) { throw new Error('取得會員資料錯誤!'); }

        memberStore.updateMember(res.data);
    }).catch((error) => {
        console.error('取得會員資料錯誤', error);
        return false;
    });

    if (!newMemberFlag) { return { name: 'MemberList', params: { page: 1 } }; }
};
```

這版有個要注意的地方：`.then` 成功時沒有 `return` 任何東西，所以 `newMemberFlag` 是 `undefined`，`!newMemberFlag` 為 `true`，**成功也會被導回列表**。要在 `.then` 最後補一行 `return true;`。（另外網址裡的 `mamber` 應該是 `member` 的筆誤。）

### 第三種：旗標，出口集中在最後
```ts
let flag = true;
try {
    const result = await sendRequest(`/api/present_pat/simpledata/${patientId}`);
    if (!result?.status) { throw new Error('取得病患資料失敗'); }

    patientStore.updatePatient(result.data);
} catch (_error) {
    console.error(_error);
    flag = false;
}

if (!flag) {
    return { name: 'PatientList' };
}
```

和第一種的差別只在「導向寫在哪」，執行結果應該一樣。但它多做了一件很重要的事：`console.error(_error)`，錯字、API 失敗都看得到了。

### Navigation aborted 要查什麼
這個訊息的意思是：從 `/` 要去 `/Member-list/1` 的這次導航，被某個守衛中斷了。也就是說，問題不一定在會員詳細頁的守衛，而可能在**導向的目標**上：

1. `MemberList` 這條路由自己有沒有 `beforeEnter`，或全域的 `beforeEach` 在這裡 `return false` 或又導向別處？
2. 會不會形成導向迴圈（A 導 B、B 又導 A）？
3. 是不是在某處呼叫了 `router.push()` 但沒處理回傳的 Promise？
4. `piniaStore.useMemberStore` 有沒有真的呼叫（`useMemberStore()`）？只拿到函式本身，`storeToRefs` 會拿不到東西。

錯誤訊息裡的路徑是 `/` 開始，表示這是**首次載入**時的導航，初始導航失敗時錯誤比較容易以 `Uncaught (in promise)` 的形式出現。

## 例子與對比

### 整理後的版本
```ts
beforeEnter: async (to) => {
    const memberStore = useMemberStore();

    const memberId = Number(to.params?.member_id) || 0;
    if (!memberId) {
        return { name: 'MemberList', params: { page: 1 } };
    }

    if (memberStore.memberState.member_id === memberId) { return; }

    const isLoaded = await loadMember(memberId);
    if (!isLoaded) {
        return { name: 'MemberList', params: { page: 1 } };
    }
};
```

```ts
// 把「拿資料」和「決定導向」拆開，拿資料只回傳成功或失敗
const loadMember = async (memberId: number): Promise<boolean> => {
    const memberStore = useMemberStore();

    try {
        const result = await sendRequest(`/api/member/${memberId}`);
        if (!result?.status) { return false; }

        memberStore.updateMember(result.data);
        return true;
    } catch (error) {
        console.error('取得會員資料錯誤', error);
        return false;
    }
};
```

| | try/catch 內 return | .then().catch() | 旗標／拆函式 |
|---|---|---|---|
| 導向寫在哪 | 分散在 catch 裡 | 最後 | 最後 |
| 錯字會不會被吞 | 會（沒 log） | 會（有 log） | 會（有 log） |
| 容易踩的坑 | 錯誤沒印出來 | 成功沒 return 也會被導走 | 少 |
| 可讀性 | 中 | 中 | 高 |

搭配 TypeScript 和 ESLint，`MemberId` 這種未宣告的變數在編輯器裡就會標紅，根本不會等到執行。

## 結論
這次的錯誤，比較可能是錯字被 catch 吞掉、加上導向目標的守衛又中斷了一次，而不是「在 catch 裡 return」本身有問題。守衛裡的非同步驗證，我的原則是：拿資料的函式只回傳成功或失敗，導向的決定集中在守衛最後，錯誤一定要印出來。

除錯的時候，~~不要相信自己的拼字~~，先相信 console。
