## 懶人包
- 最有共用價值的是**不含業務邏輯**的元件；綁了業務邏輯的共用元件，通常是「它會動，就不要動」。
- -|凡是共用就要版本管理，不想版本管理就不要共用|-。版本管理不是上 git，而是每次變更都要顧向下相容與依賴。
- 可重用性沒有 90～95%，就先開一份新的，等需求穩定再談重構。寫得直白，比寫得漂亮好維護。
- 元件深度控制在三、四層（Page → Container → Section → Atomic），多用 slot，少一層層往下鑽。
- 共用要講易用性而不是少寫幾行；要有團隊共識、要分層級，並且隨時記錄技術債。

## 觀點拆解

### 那顆會 confirm 的刪除按鈕
「點了先確認，確定才刪」聽起來很合理，包成元件好像也很合理。問題是業務邏輯一定會長：這個頁面刪除前要多問一句「底下還有子項目」、那個頁面要先打 API 檢查權限、另一個頁面確認視窗要換文案……

於是這顆按鈕開始長出 `confirmText`、`skipConfirm`、`checkChildren`、`beforeDelete`，最後你會發現，美其名是寫共用，實際上是開了一支檔案在寫窮舉 lol。一大堆條件渲染，維護起來很恐怖。

我以前有一陣子也很喜歡寫綁業務邏輯的 UI，後來發現效益很低，乾脆「直白的」寫。-|有時候適當的複製貼上和不封裝，其實更好維護|-。

### 大型團隊裡，什麼最值得共用
大型團隊協作時，最有共用價值的是**不包含業務邏輯**的元件：按鈕、輸入框、對話框的外殼、版面骨架。這些東西長相會改，但行為很穩定。

那種有業務邏輯的……它會動，就不要動。你不會想要重構或維護它，更不要說版本管理。

### 凡是共用，就要版本管理
這是我最近最大的體悟：

> 凡是共用就要版本管理，不想版本管理就不要共用。

這裡的版本管理不是「有上 git」，而是-|每一次發生變更都是一個版本|-，每一次都要處理「向下相容」和「依賴管理」：這次改動會不會弄壞其他十個用到它的頁面？那十個頁面的需求，真的跟這次改動一致嗎？

初期這蠻難體會的，我知道。等有機會碰到大型架構的重構與迭代，慢慢就會感受到。所以後來我不太追求共用，而是追求**分離**：寫得直白一點更好讀，分離好可以避免改 A 壞 B，做好解耦也能避免依賴循環。

回頭看看共用，好處除了開發快一點、code 少一點……然後產生更多問題。~~（這筆帳怎麼算都虧）~~

### 90～95% 才共用，不然先開新的
專案升級的時候我也一直在想這件事。不管是套件、自己做的 component、composable，除非可重用性超過 90～95%，不然我都先弄一個新的：

- 寧願降低耦合，不嫌麻煩先多做一份。
- 不然之後需求有調整的時候，會改得很想死。
- 等穩定了，再考慮優化重構的部分。

### 城市蓋得漂亮，擋不了隕石
以前我也很愛把差不多的東西包在一起共用，覺得乾淨、漂亮。然後需求調整、別人幫我代班，隕石掉下來。OK，世界毀滅吧~

世界末日的時候，城市蓋得再漂亮也沒用，隕石落下，全毀。比較實在的做法是**分區隔離、分艙隔離**：隕石來了，壞的那一區拋棄、蓋新的就好，其他區照常營業。

要能快速應對「隨時可能有隕石」的狀況，群組裡整理出的做法是：

1. 不要太快封裝「功能正常、但只是邏輯相似」的元件。
2. 先求功能寫完、運作正常，不要把時間都花在程式碼好看，但邏輯要清楚。
3. 專案架構的元件深度不要超過三層（我自己不想超過三層）。
4. 隨時記錄技術債的存在點：那些迫於時間壓力、特定需求，讓你很無奈必須妥協的東西，都寫下來。

### 元件深度與 slot
以前寫 Vue 時，我通常不會讓專案出現超過 4 層的深度：

```
Page
└─ Container
   └─ Section
      └─ Atomic
```

這幾層很夠用了。一支檔案行數多一點沒關係，分層清楚、有拆 composable 就很夠。Vue 搭配 slot 可以大量減少元件深度，不用一層層往下找。

### 共用的四個原則
最近一年對「共用」最大的感受：

1. 共用應該強調的是**易用性**，而不是可以少寫 code 就好。
2. 在易用的前提下，產品專案內部的共用都是動態的，迭代速度與幅度相對快。不要抱著「久久更新一次」的心態處理共用，應該替專案的共用**分層級**。
3. 有了上面兩點，共用原則與共識就很重要。不然專案裡會出現一堆同事各自的共用手法，某種程度上反而讓專案更髒、更難用。
4. 共用的前提是**解耦**。共用區塊要盡可能減少狀態處理，除非狀態的生命週期已經非常成熟，不然真的是複製貼上才不會突然天外飛來 bug 單。

### 共用的範圍也要設計
簡單的共用可能是樣式共用、資料共用，或是**共用範圍**。例如甲元件只會在 A 頁面內部共用，那這個檔案該放哪、怎麼命名，就要好好想一下。

常見的翻車情況有兩種：

- 只在 A 頁面共用的東西放在 global 層級，命名也沒處理好，後面的人分不清楚，直接動手改下去，炸爛同事。
- 不管共用性質直接 import 拿來用，後面需求一改，莫名其妙接到 bug 單。

### 不要把不太一樣的東西包進同一個共用邏輯
比方說有個函式，會產出一個固定格式的物件，但輸入端卻可以接很多種不同格式的資料，甚至直接吃某個元件的狀態。這樣這個函式的耦合會很重。

用元件粗暴一點的說法就是：-|把東西處理好再 prop 給子層|-，不要把一堆狀態打進子層讓它自己處理。

### 最後：工具要熟
IDE 功能很好用，資料夾分層管理很好用。稍微研究一下，專案變大的時候會幸福很多。我後來發現真的很多人連工具都不熟，反而因此增加專案管理的難度 Orz...

## 例子與對比

### 做法 A：把業務邏輯包進共用按鈕
```vue
<!-- DeleteButton.vue：業務邏輯住在 UI 元件裡 -->
<script setup lang="ts">
const props = defineProps<{
    confirmText?: string;
    skipConfirm?: boolean;
    checkChildren?: boolean;
    childCount?: number;
}>();
const emit = defineEmits<{ 'delete-click': [] }>();

const onClick = () => {
    if (props.checkChildren && (props.childCount ?? 0) > 0) {
        if (!window.confirm('底下還有子項目，確定要一起刪除？')) { return; }
    } else if (!props.skipConfirm) {
        if (!window.confirm(props.confirmText ?? '確定要刪除嗎？')) { return; }
    }

    emit('delete-click');
};
</script>

<template>
    <button class="btn btn--danger" type="button" @click="onClick">
        <slot>刪除</slot>
    </button>
</template>
```

每多一個頁面的特殊需求，就多一個 prop、多一個分支。三個月後沒人敢動它。

### 做法 B：UI 元件只管長相，業務邏輯留在頁面
```vue
<!-- BaseButton.vue：它不知道「刪除」是什麼 -->
<script setup lang="ts">
defineProps<{ variant?: 'primary' | 'danger' }>();
</script>

<template>
    <button class="btn" :class="variant ? `btn--${variant}` : ''" type="button">
        <slot />
    </button>
</template>
```

```vue
<!-- 頁面：這個頁面的刪除規則，就寫在這個頁面 -->
<script setup lang="ts">
const props = defineProps<{ id: number; childCount: number }>();
const emit = defineEmits<{ deleted: [id: number] }>();

const onDelete = () => {
    const message = props.childCount > 0
        ? '底下還有子項目，確定要一起刪除？'
        : '確定要刪除嗎？';
    if (!window.confirm(message)) { return; }

    emit('deleted', props.id);
};
</script>

<template>
    <BaseButton variant="danger" @click="onDelete">刪除</BaseButton>
</template>
```

`BaseButton` 幾乎不會因為需求而改；頁面的規則改了，只會動到那一個頁面。這就是分艙隔離。

| | 綁業務邏輯的共用元件 | 純 UI 元件 + 頁面自己的邏輯 |
|---|---|---|
| 開發初期 | 快，少寫幾行 | 每頁多寫幾行 |
| 只改一個頁面的需求 | 改共用元件，擔心其他頁面 | 只改那個頁面 |
| 版本管理 | 每次改都要顧向下相容 | 幾乎不用 |
| 交接給別人 | 要先讀懂所有分支 | 打開頁面就看得到規則 |

## 結論
共用本身沒有錯，錯的是在需求還沒穩定的時候，就把「看起來差不多」的東西綁在一起。先把東西分開、寫直白、記下技術債，等它真的穩定到九成以上都長一樣，再來談共用與重構。

畢竟隕石不會先發公告才掉下來，你能做的，就是讓它只砸壞一間房子。
