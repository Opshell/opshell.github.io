常見的情況是：列表頁點進詳細頁，再按上一頁回來，列表又轉一次 Loading、篩選條件也不見了。要解決「回來時東西還在」，大家第一個想到的常常是 `<KeepAlive>`，但它不一定是最好的答案。這篇整理三種留存方式各自適合留什麼，寫給正在決定要用哪一種的人。
:::

## 懶人包

- 要留的東西分兩種：**API 資料**和**使用者操作的 UI 狀態**，先分清楚再挑工具。
- API 資料交給快取：用 `TanStack Query` 之類的工具並設定 `staleTime`，回上一頁不用再等 Loading，也省流量。
- UI 狀態（篩選條件、分頁、勾選）放 store，或乾脆放網址的 query。
- `<KeepAlive>` 會把整個元件留在記憶體，還多了一組生命週期要管，-|是最後的選擇|-。

## 觀點拆解

### 先分清楚：你要留的是什麼

「回來時東西還在」其實包含兩種東西：

1. **API 資料**：列表的內容、詳細頁的資料。來源在後端，前端只是暫存。
2. **UI 狀態**：使用者選的篩選條件、在第幾頁、捲到哪、勾了哪幾筆。來源是使用者的操作。

這兩種東西壽命不同、來源不同，用同一把槌子去敲，通常會敲到手。

### API 資料：我還是鼓勵要設定 staleTime

我還是鼓勵要設定 `staleTime`，畢竟這才是 cache 的價值。

`TanStack Query` 的預設 `staleTime` 是 0，意思是資料一拿到就算「過期」，元件重新掛載時會在背景再打一次 API。如果你沒設定，等於有快取卻每次都重抓。

真的就是有白目喜歡在兩頁跳來跳去，你看流量會不會也跳跳跳。而且有時候手殘回到上一頁還要等 Loading，真的很煩。

設了 `staleTime`，在這段時間內回來就直接拿快取，畫面瞬間出來，後端也少挨幾刀。

### UI 狀態：store 或網址

如果是使用者操作的 UI 狀態，確實可以直接考慮 store。篩選條件放進 Pinia，換頁回來元件重新建立，從 store 讀回來就好。

更進一步，篩選和分頁這種「想分享給別人看」的狀態，可以直接放網址的 query（`?page=3&status=done`），重新整理、複製連結都還在。

### KeepAlive：最後的選擇

再說，我沒有很愛用 `KeepAlive`。除非我想暫存 component 狀態，不然大部分暫存 API data 就夠了。`KeepAlive` 會存過多不必要的資訊，浪費記憶體。所以 `KeepAlive` 這真的是最後的選擇。

`KeepAlive` 另一個問題是生命週期。你要手動去管理額外的生命週期（`onActivated`、`onDeactivated`），增加元件維護的心智負擔。像是 `watch`，在 `<KeepAlive>` 處於 deactivated 狀態時還是會繼續運作，這要特別注意才不會發生預期之外的事。

副作用多一點，還要管理 memory leak 的問題：計時器、WebSocket、全域事件監聽，元件沒被卸載就不會自己清掉。

## 例子與對比

### API 資料：useQuery + staleTime

```ts
import { useQuery } from '@tanstack/vue-query';
import type { Ref } from 'vue';

export function useOrderList(page: Ref<number>) {
    return useQuery({
        queryKey: ['orders', page],
        queryFn: () => fetchOrders(page.value),
        staleTime: 5 * 60 * 1000 // 5 分鐘內回來直接用快取
    });
}
```

### UI 狀態：放 store

```ts
// stores/orderFilter.ts
import { defineStore } from 'pinia';
import { ref } from 'vue';

export const useOrderFilterStore = defineStore('orderFilter', () => {
    const status = ref<'all' | 'pending' | 'done'>('all');
    const page = ref(1);

    function reset() {
        status.value = 'all';
        page.value = 1;
    }

    return { status, page, reset };
});
```

列表頁直接讀 store，回來時條件還在；再把 `page` 丟給上面的 `useOrderList`，資料也是快取的，完全不用轉圈。

### 真的要 KeepAlive 的話

```vue
<template>
    <RouterView v-slot="{ Component }">
        <KeepAlive :include="['OrderEditor']" :max="3">
            <component :is="Component" />
        </KeepAlive>
    </RouterView>
</template>
```

用 `include` 只留真正需要的元件（例如填到一半的長表單），`max` 限制數量。元件裡的計時器、輪詢記得在 `onDeactivated` 停掉、`onActivated` 再開。

### 對比

| | API 快取（`staleTime`） | store / 網址 | `KeepAlive` |
|---|---|---|---|
| 適合留 | 後端資料 | 使用者的 UI 狀態 | 整個元件的現場（含 DOM 與內部狀態） |
| 記憶體 | 只有資料 | 只有狀態 | 整個元件實體 |
| 額外生命週期 | 無 | 無 | `onActivated` / `onDeactivated` |
| 副作用風險 | 低 | 低 | `watch`、計時器在背景繼續跑 |
| 重新整理後 | 沒了（除非另外持久化） | store 沒了、網址還在 | 沒了 |

## 結論

回上一頁要快、要記得條件，大部分時候是「API 資料有快取 + UI 狀態有地方放」就解決了。`staleTime` 設好、篩選條件放 store 或網址，`KeepAlive` 留給那種真的要保住整個現場的長表單。

能用快取解決的就別整個元件冷凍起來，冰箱塞太滿，門是會關不上的。
