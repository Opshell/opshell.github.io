::: info 這篇的脈絡
寫 code 寫久了，常常會在 Code Review、查 bug 或看別人專案的時候，撞到一些「好像聽過、但說不清楚」的名詞。當下沒空深究，過了就忘。
這篇就是把這些線索先釘在牆上：一部分是之後想深挖的關鍵字，一部分是用一個載入 reCAPTCHA 的 composable，實際把其中幾個線索拆開來看。寫給跟我一樣，想從「能動」往「健壯」走的前端工程師。
:::

## 懶人包

- 這份清單分四條線：Vue 專案的架構（功能導向、FSD）、程式碼品質（健壯性、Code Smell、Strategy Pattern）、Code Review 的吵架題（YAGNI、SSoT）、JS 的非同步細節（IIFE、Floating Promise）。
- 動態載入第三方 script 時，用「Promise Singleton」把**載入中的 Promise** 存起來，而不是存一個 boolean，就能解掉多個元件同時呼叫的 race condition。
- 把 `async` 函式丟給一個只期待 `() => void` 的 callback，回傳的 Promise 就沒人接，這就是 Floating Promise。
- 用 async IIFE 包起來可以讓型別閉嘴，但 Promise 其實還是飄著；更乾淨的做法是在 callback 裡直接 `.then().catch()`。

## 觀點拆解

### 線索一：Vue 的開發優化——功能導向

Vue 3 社群裡越來越推崇-|功能導向 (Feature-Oriented)|-的資料夾結構：不是把所有元件丟 `components/`、所有 store 丟 `stores/`，而是按「功能」切，一個功能自己的元件、狀態、API 放在一起。

再往嚴格一點走，就是 **Feature-Sliced Design (FSD)**：把專案切成固定的層級（app、pages、widgets、features、entities、shared），規定只能上層引用下層，每個切片只透過 `index.ts` 對外。
這兩個的差別很像「整理房間」跟「搬進有管委會的社區」：前者自己開心就好，後者有規約，但人一多就知道規約的好。

### 線索二：程式碼品質

- **程式碼更健壯 (Robust)**：不是「正常情況能跑」，而是「網路斷了、使用者連點、script 被擋」的時候也不會炸。下面的 `useRecaptcha` 就是一個很好的練習題。
- **程式碼異味 (Code Smell)**：程式碼還能跑，但聞起來不對——巨大的函式、一堆 `if/else` 判斷類型、同一段邏輯複製三份。它不是 bug，是 bug 的溫床。
- **Strategy Pattern**：專治「一堆 `if/else` 判斷類型」那種異味。把每種做法包成一個策略，用一張對照表取代判斷式，新增一種做法就是新增一個物件，不用回頭改原本的程式。

### 線索三：Code Review 的衝突場景

Code Review 最常吵的，往往不是對錯，而是-|「要不要現在就做」|-跟「這份資料到底以誰為準」：

- **YAGNI (You Ain't Gonna Need It)**：「未來可能會用到」通常不會用到。為了想像中的需求先加的抽象層，最後只會變成維護成本。
- **SSoT (Single Source of Truth)**：同一份資料只能有一個權威來源。前端自己再存一份後端已經算好的狀態、兩個 store 各記一份使用者資料，遲早對不上。

這兩條會互相拉扯：為了守 SSoT 多抽一層，有人會跳出來喊 YAGNI。我的看法是：**資料一致性出事的代價通常比多一層抽象高**，所以 SSoT 優先；但抽象只做到「現在需要的那一層」。

### 線索四：JS 的非同步細節

- **IIFE（立即執行函式）**：定義完馬上執行的函式，`(() => { ... })()`。在 ES Module 時代比較少用來隔離作用域了，但在「這裡不能用 `async`，我又想用 `await`」的時候還是很常見。
- **Floating Promise**：一個 Promise 被建立了，但沒有人 `await`、沒有 `.then()`、也沒有 `.catch()`。它失敗的時候，錯誤會直接變成 unhandled rejection，而且你很難知道是誰丟的。

後兩個線索，剛好在下面這個例子裡一次遇到。

## 例子與對比

### 需求：只載一次的 reCAPTCHA

登入、註冊、忘記密碼三個表單都要用 reCAPTCHA Enterprise，但它的 script 很肥，我們不想在首頁就載。所以需求是：

1. 第一次需要驗證的時候才載入 script。
2. 兩個元件同時呼叫，也只能載一次。
3. 載入失敗，下次呼叫要能重試。

原本的草稿裡，模組頂層的宣告是這樣（作者留下的註解）：

<!-- import { ref } from 'vue'; // 如果未來需要 loading 狀態可以引入，目前純 JS 邏輯即可

const RECAPTCHA_URL = `https://www.google.com/recaptcha/enterprise.js?render=${__RECAPTCHA_SITE_KEY__}`; -->

<!-- // 使用 Promise 來保存載入狀態，而不僅僅是 boolean
// null = 未開始, Promise = 載入中或已完成
let loadPromise: Promise<void> | null = null; -->

```ts
const RECAPTCHA_URL = `https://www.google.com/recaptcha/enterprise.js?render=${__RECAPTCHA_SITE_KEY__}`;

// 使用 Promise 來保存載入狀態，而不僅僅是 boolean
// null = 未開始, Promise = 載入中或已完成
let loadPromise: Promise<void> | null = null;
```

重點在 `loadPromise` 放在**模組頂層**、composable 外面。ES Module 只會被執行一次，所以不管幾個元件呼叫 `useRecaptcha()`，大家拿到的都是同一個 `loadPromise`。順帶一提，那個 `import { ref }` 被註解掉也是對的，目前用不到，這就是 YAGNI。

::: tip
`__RECAPTCHA_SITE_KEY__` 是用 Vite 的 `define` 在建置時替換的常數，記得在 `.d.ts` 裡宣告它的型別，以及 `window.grecaptcha` 的型別，不然 TypeScript 會抱怨。
:::

### 為什麼存 Promise，不存 boolean

如果用 `isLoaded = true/false`，會有一段尷尬的空窗：script 已經插進去、但還沒載完。這時第二個元件看到 `false`，又插了一次 script。
存 Promise 就沒有這個問題：載入中的人拿到同一個 Promise 一起等，載完的人拿到已經 resolve 的 Promise 直接過。這招就叫 **Promise Singleton**。

```ts
export function useRecaptcha() {
    const siteKey = __RECAPTCHA_SITE_KEY__;

    /**
     * 負責載入 Script 的核心邏輯
     * 利用 Promise Singleton 模式解決 Race Condition
     */
    const loadScript = (): Promise<void> => {
        // 如果 window 中已經有物件，視為已載入 (可能是其他地方引入的)
        if (window.grecaptcha?.enterprise) {
            return Promise.resolve();
        }

        // 如果已經在載入中（但還沒完成），直接回傳同一個 Promise
        if (loadPromise) {
            return loadPromise;
        }

        // 開始新的載入流程
        loadPromise = new Promise((resolve, reject) => {
            const script = document.createElement('script');
            script.src = RECAPTCHA_URL;
            script.async = true;
            script.defer = true; // 建議加上 defer

            script.onload = () => {
                resolve();
            };

            script.onerror = (err) => {
                // 失敗時重置 promise，讓下次呼叫有機會重試
                loadPromise = null;
                console.error('[Recaptcha] Script load failed:', err);
                reject(err);
            };

            document.head.appendChild(script);
        });

        return loadPromise;
    };

    /**
     * 執行驗證並取得 Token
     */
    const execute = async (action: string = 'login'): Promise<string> => {
        try {
            await loadScript();

            if (!window.grecaptcha?.enterprise) {
                console.warn('[Recaptcha] grecaptcha.enterprise is missing after load.');
                return '';
            }

            return await new Promise<string>((resolve) => {
                window.grecaptcha!.enterprise.ready(async () => {
                    try {
                        const token = await window.grecaptcha!.enterprise.execute(siteKey, { action });
                        resolve(token);
                    } catch (error) {
                        console.error('[Recaptcha] Execution failed:', error);
                        // 根據業務需求，這裡可以 resolve('') 或是 throw error
                        resolve('');
                    }
                });
            });

        } catch (e) {
            console.error('[Recaptcha] Unexpected error:', e);
            return '';
        }
    };

    return { execute };
}
```

`onerror` 裡把 `loadPromise` 重設成 `null` 是需求 3 的關鍵：不然一次失敗，之後每次呼叫都會拿到那個已經 reject 的 Promise，永遠載不起來。
~~（另外動態插進去的 script 本來就是非同步載入，`defer` 加了也沒什麼作用，不過留著無害。）~~

### 問題：`ready(async () => ...)` 是一顆飄著的 Promise

上面能跑，但 `typescript-eslint` 的 `no-misused-promises` 會在 `ready(async () => ...)` 那行亮紅燈。
原因是 `ready` 期待的是一個回傳 `void` 的 callback，它根本不會去管你回傳了什麼。你塞一個 `async` 函式進去，它回傳的 Promise 就沒人接——這就是 Floating Promise。
這裡因為裡面有 `try/catch`，實際上不會漏錯誤，但規則看不出來，下一個改這段的人也不一定看得出來。

### 解法 A：async IIFE

原本草稿的修法，是讓 `ready` 收到普通的箭頭函式，再在裡面用 async IIFE 處理非同步：

```ts
const execute = async (action: string = 'login'): Promise<string> => {
    try {
        await loadScript();

        if (!window.grecaptcha?.enterprise) {
            console.warn('[Recaptcha] grecaptcha.enterprise is missing after load.');
            return '';
        }

        return await new Promise<string>((resolve) => {
            // 1. 去掉這裡的 async，改成普通的箭頭函式
            window.grecaptcha!.enterprise.ready(() => {
                // 2. 在這裡面啟動一個 async IIFE (Immediately Invoked Function Expression)
                // 這樣 ready 接收到的是 void，而我們在內部自行處理 Promise
                (async () => {
                    try {
                        const token = await window.grecaptcha!.enterprise.execute(siteKey, { action });
                        resolve(token);
                    } catch (error) {
                        console.error('[Recaptcha] Execution failed:', error);
                        resolve('');
                    }
                })();
            });
        });

    } catch (e) {
        console.error('[Recaptcha] Unexpected error:', e);
        return '';
    }
};
```

`no-misused-promises` 安靜了，但老實說，IIFE 回傳的那個 Promise **還是飄著**，只是換了個地方飄。如果有開 `no-floating-promises`，它會換成抓這一行。要嘛在前面加 `void` 明講「我知道，我故意的」：

```ts
void (async () => {
    // ...同上
})();
```

### 解法 B：直接用 `.then().catch()`

既然 callback 本來就不能是 async，那乾脆不要用 `await`，讓 Promise 鏈自己把錯誤收好：

```ts
return await new Promise<string>((resolve) => {
    window.grecaptcha!.enterprise.ready(() => {
        window.grecaptcha!.enterprise.execute(siteKey, { action })
            .then(resolve)
            .catch((error: unknown) => {
                console.error('[Recaptcha] Execution failed:', error);
                resolve('');
            });
    });
});
```

| 做法 | `no-misused-promises` | `no-floating-promises` | 讀起來 |
| --- | --- | --- | --- |
| `ready(async () => ...)` | 報錯 | 不報 | 最直覺，但騙了型別 |
| async IIFE | 不報 | 報錯（除非加 `void`） | 多一層包裝 |
| `.then().catch()` | 不報 | 不報（有 `.catch` 算有處理） | 最短，錯誤去向一眼看到 |

我會選 B。不是因為 `await` 不好，而是在一個「不能 async」的地方硬塞 async，本身就是一種 Code Smell。

## 結論

這份清單的每一條線索，單獨看都只是一個名詞；但像 `useRecaptcha` 這樣一段不到一百行的程式，就能同時碰到 race condition、Promise Singleton、Floating Promise 和 IIFE，順便還示範了一次 YAGNI。
所以與其一次把這些名詞全部讀完，不如先把它們記在牆上，下次在自己的程式碼裡撞見，再回來拉那條線。
