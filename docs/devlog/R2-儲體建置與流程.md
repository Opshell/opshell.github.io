# Cloudflare R2 儲體建置與流程

2026-09-28 把叮咚功能演示的影片從 git 搬到 R2 時整理的。之後相簿要做自動上傳，或者有新的素材要放 R2，照這份做。

## 為什麼放 R2，不放 git

- 影片、照片這類大檔進 git，**每改一次就多一份永久的歷史**。演示重錄三次，官網倉庫就到 74 MB，其中 50 MB 是演示。
- R2 沒有流出流量費，接上自訂網域之後還有 Cloudflare 的 CDN 快取。
- 倉庫只留「目錄」：`demos.json` 記錄每支影片在 R2 上的檔名，建置和 CI 都不需要碰到影片本身。

## 現有的儲體

| 儲體 | 網域 | 放什麼 | 怎麼上傳 | 權杖 |
|---|---|---|---|---|
| `dindon-demo` | `https://dindon-demo.opshell.me/` | 叮咚功能演示：影片、封面、目錄縮圖，放在根目錄 | `pnpm dindon:demos`（自動） | 只套用到 `dindon-demo`，放在 `.env.local` 的 `R2_DINDON_*` |
| `opshell-gallery` | `https://image.opshell.me/` | 相簿：`raw/` 原圖、`thumbs/` 縮圖 | **手動**（後台拖拉或 S3 Browser），自動化列在待辦 | 舊的 `Upload-Script`（2026-01-21），沒有程式在用 |

**一個用途一個儲體**：權杖可以只開放給單一儲體，萬一外流，影響範圍也只有那一個；用量和費用可以分開看；
哪天要換網域或搬家，也能整個儲體一起處理。

## 一、建儲體（Cloudflare 後台）

1. **R2 物件儲存空間 → 建立儲體**。名稱只能用小寫英文、數字、短橫線，例如 `dindon-demo`。位置選自動。
2. **接自訂網域**：進儲體 → 設定 → 自訂網域 → 新增，輸入例如 `dindon-demo.opshell.me`。
   - `opshell.me` 本來就在 Cloudflare 上，DNS 紀錄會自動加，不用手動設定。
   - **不要用內建的 `r2.dev` 網址**，它有流量限制，官方說只適合開發測試。
3. **CORS**：只用 `<img>`、`<video>` 直接顯示的話**不用設定**。要用 JS `fetch` 讀檔、或畫進 canvas 讀像素，才需要設定
   （相簿的 `opshell-gallery` 有設，規則在草稿文章 `cloudflare-r2-容器設定-圖床建置.md`）。

## 二、建上傳權杖

1. R2 首頁 → **管理 API 權杖** → **建立 Account API 權杖**（Cloudflare 建議用這種；另一種 User API 權杖會跟著個人帳號，人離開組織就失效）。
2. 權限選「**物件讀取和寫入**」，套用範圍**只選要上傳的那個儲體**。
3. 建好後頁面會顯示三樣東西，**Secret 只顯示這一次**，當場存好：
   - Access Key ID
   - Secret Access Key
   - S3 端點：`https://<帳號 ID>.r2.cloudflarestorage.com`（**不含**儲體名稱）
4. 寫進**官網倉庫根目錄**的 `.env.local`：

   ```
   R2_DINDON_ENDPOINT=https://<帳號 ID>.r2.cloudflarestorage.com
   R2_DINDON_ACCESS_KEY_ID=…
   R2_DINDON_SECRET_ACCESS_KEY=…
   ```

   - `.gitignore` 有排除 `.env` 和 `.env.*`，不會進版控。**2026-09-28 以前只排除 `.env`**，`.env.local` 差點被提交，已經補上。
   - 金鑰不要貼到對話裡。Claude 要確認時只看變數名稱，不看值。
   - Vite 只會把 `VITE_` 開頭的變數送到瀏覽器，`R2_*` 不會出現在網站上。不過這個網站本來就不能有任何祕密，所以也不要取 `VITE_` 開頭的名字。

## 三、上傳腳本怎麼運作（`scripts/sync-dindon-demos.mjs`）

```bash
pnpm dindon:demos --dry     # 只列出要傳哪些檔案，不上傳、不改 demos.json
pnpm dindon:demos           # 上傳，寫 demos.json
pnpm dindon:demos --prune   # 順便刪掉 R2 上已經不在清單裡的舊檔
```

1. 讀 App 倉庫本機的 `store/demos/index.json`（前端 Claude 錄好的目錄），檢查列出來的檔案都在。
2. 每個檔案的檔名加上**內容雜湊**：`02-dedupe.mp4` 變成 `02-dedupe.cc1ede89.mp4`。目錄縮圖由封面縮成 240 寬的 webp。
3. 逐一向 R2 查詢（HEAD）：已經有同名的就跳過。同名代表內容相同，所以重跑很快，只會傳新錄的。
4. 上傳時帶 `Cache-Control: public, max-age=31536000, immutable`（快取一年）。
5. **全部傳完才寫 `demos.json`**（加上 `mediaBase` 與雜湊檔名），網頁不會指到還沒上傳的檔案。
6. 列出 R2 上不在清單裡的舊檔；加 `--prune` 才刪。預設留著，是為了讓還開著舊頁面的人不會突然看不到影片。

**為什麼檔名要帶雜湊**：可以放心快取一年。重錄之後內容變了，檔名跟著變，瀏覽器和 CDN 會抓新的，不會有人看到舊影片。
如果不用雜湊、同名覆蓋，快取就只能設很短，不然會看到舊檔。

簽章用 `aws4fetch`（Cloudflare 文件推薦給 R2 的小套件，沒有其他依賴），打的是 S3 相容 API：
`<端點>/<儲體>/<檔名>`，區域填 `auto`。

## 四、重錄之後的日常流程

1. 前端 Claude 錄好，在溝通板回覆。
2. 官網跑 `pnpm dindon:demos`，只會傳有變的檔案。
3. commit `docs/features/dindon/demo/demos.json`，push 就上線。
4. 偶爾跑一次 `--prune`，清掉很久以前的舊版本。

## 五、上傳後怎麼驗證

- 每個檔案經**公開網域**打得開，而且大小跟原檔一致（2026-09-28 的 108 個都檢查過）。
- 影片支援分段下載：`curl -H 'Range: bytes=0-1023' <網址>` 要回 **206**，不然影片不能拖進度條。
- 回應標頭有 `cache-control: … immutable`；第二次請求 `cf-cache-status: HIT`，代表 CDN 有快取。
- 建置後在瀏覽器打開演示頁：縮圖從 R2 載入，點開影片會播放。

## 六、搬家（從 git 移到 R2）的順序

1. 腳本先上線，但網頁在 `demos.json` 沒有 `mediaBase` 時照舊讀 `docs/public`，這段時間網站不會中斷。
2. 建儲體、網域、權杖，實際上傳，照第五節驗證。
3. 刪掉倉庫裡的副本、把網頁的退回寫法拿掉，push。
4. （可選）改寫 git 歷史，把舊檔從所有 commit 裡清掉，見第八節。

## 七、踩過的坑

- **測試不能沒有金鑰**：真正上傳前，先用一個假的 S3 伺服器跑過：首次傳完、再跑全部跳過、`--prune` 只刪舊檔、每個請求都有簽章。
- **`vitepress preview` 要在建置完成後才啟動**。在建置途中啟動的話，它記住的是舊的檔案清單，新的 JS 一律 404，看起來像頁面沒有啟動。
- 相簿的舊文章寫網域是 `images.opshell.me`，實際在用的是 `image.opshell.me`（程式碼為準）。

## 八、清理 git 歷史

見同資料夾的開發記錄 2026-09-28 那一節：用 `git filter-repo` 從所有 commit 移除 `docs/public/images/dindon/demos/`、force push，
再依對照表替換文件裡的 commit 編號。改寫前的完整備份在 `~/WWW/DinDon-backups/`。
