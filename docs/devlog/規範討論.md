# 前端開發規範：討論紀錄

對象：`docs/pages/article/code-sea/typescript/zod-schema-型別使用規範拷貝.md`（v4.0，三份裡最新、已吸收舊版的「下一版本更新內容」）。
另外兩份（同資料夾的 `README.md`、`zod-schema-型別使用規範.md`）是舊版，收斂完就退場。

**前提（2026-09-27 使用者定的）**：之後的工作與專案都以這份規範為**通用準則**。部落格也是專案之一，
所以規範與部落格衝突時，要在規範裡定出一個答案，不各走各的。

討論分四輪：① 地基 ② 資料層 ③ 伺服端資料 ④ 落地（工具強制、放哪、發佈）。

---

## 第一輪：地基（2026-09-27）

| 題目 | 決定 | 理由 |
|---|---|---|
| 結構 | **核心章＋條件章**。核心（目錄與檔名、CSS／SCSS、SFC 組織、TS 基本）所有專案必守；條件章（Zod 資料層、TanStack 伺服端資料、表單）用到才適用 | 部落格沒有 router、Pinia、TanStack，硬導入成本高、收益低 |
| 靜態變體 | **`--modifier` 與 `is-state` 分工**：props 決定的固定規格用 `--`，互動中會變的用 `is-` | 語意清楚，是規範第二章的核心論點。部落格現況 `&--` 12 處、`&.is-` 82 處，要改的是其中屬於「變體」的 `is-` |
| 檔名 | **`.vue` 一律 PascalCase**，`.ts` 小駝峰，composable `useXxx.ts` | Vue 官方風格指南的建議；部落格 9-22 已統一成這樣，規範改一行 |
| Zod 版本 | **Zod 4** | 新專案都會是 4：`z.stringbool()` 解決網址布林值、`z.enum` 直接吃 TS enum（`z.nativeEnum` 不再建議）。範例照 4 改 |

**部落格用 Zod 4 的地方**（屬於條件章的適用者：有 Zod 資料層，沒有 TanStack／router）：

1. 文章 frontmatter：建置時驗證（9-25 的 Belief 整頁空白就是 `createdAt` 被讀成 Date 物件），不增加網頁 JS
2. 叮咚後台 `dashboard/api.ts`：待辦第 7 步，照 Raw → Parser 流程接
3. 同步腳本讀進來的 JSON（演示 `index.json`）：格式不對就擋

瀏覽器端要用時考慮 `zod/mini`。

### 第一輪留給規範本身要改的

- [ ] 第一章檔名規範改成：`.vue` PascalCase、`.ts` camelCase、`useXxx.ts`
- [ ] 第二章補：樣式包在唯一的頂層 class、不用 `scoped`（理由與三個坑見部落格 `web-code-style` skill）、顏色用新式寫法
- [ ] `[P]` 的意思統一成「region 標題標記」，不再寫「Process 或 Private」
- [ ] 範例改成 Zod 4 寫法；`z.coerce.boolean()` 用在網址參數的 bug 改成 `z.stringbool()`
- [ ] 部落格：屬於「變體」的 `is-` 改成 `--`（盤點後再動）

## 第二輪：資料層（2026-09-27）

| 題目 | 決定 | 備註 |
|---|---|---|
| `...Output` 命名 | **維持原名** | 規範裡加一行：`...Output` 指「API 回來、解析前的原始形狀」（`z.input<Parser>`），跟 Zod 的 `z.output`（轉換後）不同；解析後的型別就是核心型別（`Product`） |
| parse 失敗 | **丟出專用錯誤** | Repository 一律經 `parseResponse(schema, data, endpoint)`：`safeParse` 失敗就丟 `ApiSchemaError`（帶端點與 Zod 錯誤明細），走一般錯誤流程（TanStack error 狀態、畫面「資料格式有誤」）；開發時印出哪個欄位不對，正式環境送錯誤回報 |
| 多餘欄位 | **`z.object`（丟掉）** | Zod 4 預設行為。後端加欄位前端不會壞，也用不到沒定義的東西；`looseObject`、`strictObject` 不用 |
| `utils/zod.ts` | **Claude 寫標準版** | 型別層用 type-fest 的 `CamelCasedPropertiesDeep`／`SnakeCasedPropertiesDeep`，執行層遞迴轉 key（陣列、巢狀照轉，`Date` 等非純物件不動），附單元測試；規範附完整實作 |

### 第二輪留給規範本身要改的

- [ ] 第四章 3-2 的 `...Output` 加上跟 `z.output` 的區別說明
- [ ] 新增一節「解析失敗」：`parseResponse`、`ApiSchemaError`、開發與正式環境的差別
- [ ] 第四章 7 注意事項補：物件一律 `z.object`，不用 `looseObject`／`strictObject`
- [ ] 附錄：`utils/zod.ts` 完整實作與測試

## 第三輪：伺服端資料（2026-09-28）

舊版這章只有標題、v4.0 整章拿掉，這輪從零定。

| 題目 | 決定 | 備註 |
|---|---|---|
| query key 與查詢設定 | **每個 feature 一支 `queries.ts`** | 用 TanStack v5 的 `queryOptions()` 把 key 與 queryFn 綁在一起，key 有階層（`all → lists → list(params)`、`all → detail(id)`）；元件只寫 `useQuery(productQueries.list(searchParams))` |
| 寫入後的更新 | **預設失效重抓** | mutation 成功後 `invalidateQueries({ queryKey: productQueries.all() })`。樂觀更新是例外：只用在拖曳排序、勾選這類要即時手感的地方，而且要寫失敗時怎麼還原 |
| 全域預設值 | **寫進規範** | `staleTime` 30 秒（預設 0 會一切頁面就重抓）；`ApiSchemaError` 與 4xx 不重試（重試也不會變對），5xx 與網路錯誤重試 2 次 |

### 第三輪留給規範本身要改的

- [ ] 新增第五章「伺服端資料（TanStack Query）」：`queries.ts` 範例、key 階層、失效策略、樂觀更新的條件、QueryClient 預設值
- [ ] 第三章 SFC 範本改用 `productQueries`，拿掉元件裡手寫的 key；`mutationFn` 的 `unknown` 改成規範的 `...Input` 型別
- [ ] 範本裡「搜尋」區塊去清「批次操作」的 `selectIds`：改成批次區塊自己 `watch(searchParams)` 清空，區塊之間不互相伸手
- [ ] 目錄結構加 `queries.ts`

## 定稿（2026-09-28，草稿待使用者確認）

寫在 `docs/pages/article/code-sea/developer/前端開發規範.md`（v5.0.0，`isPublished: false`，開頭有草稿提示擋住發文工具）。
範例程式全部在暫存專案實際跑過：zod 4.6、@tanstack/vue-query 5.104、vee-validate 4.15、type-fest 5.10，`vue-tsc` 通過、16 個測試通過。

寫的過程中發現、已經寫進規範的：

- **Zod 4 的 `.pipe()` 要求後者的輸入型別能被前者輸出滿足**：核心 Schema 放 `.default()` 會型別錯誤 → 核心不放 default
- **Raw 的列舉寫 `z.string()` 會讓 pipe 失敗** → Raw 也用同一個 enum
- **`@vee-validate/zod` 只支援 Zod 3**，vee-validate 5 還在 beta → 自寫 `toFormSchema()` 轉接器
- **縮寫 `userID` 在 type-fest 與執行層轉出來不同**（`user_id` vs `user_i_d`）→ 執行層改成跟型別一致；規範定「縮寫只大寫第一個字母」
- lint 試跑部落格：檔名只有 3 支違規（`ArticleTOC.vue`、`useTOC.ts`、`work-experience.data.ts`），class 格式 1 處（VitePress 的 `.Layout`），scoped 0

還待使用者決定的兩項（規範裡用「待定」框標著）：手寫 interface 的 `i`／`t` 前綴要不要統一；Pinia 是否只放客戶端狀態。

## 原本的定稿清單

照四輪的「留給規範本身要改的」清單改 v4.0，產出一份正式檔名的規範：

1. 結構改成核心章（一～四）＋條件章（五 Zod、六 TanStack、七 表單）＋附錄（不採用與為什麼、`utils/zod.ts`、工具設定）
2. 每條規則標「工具擋」或「review」
3. 開頭補「這篇的脈絡」；作者只寫 Opshell
4. 範例全部照 Zod 4 與 TanStack v5 寫、實際跑過型別檢查
5. 定稿後刪掉舊的兩份，放進發文排程
