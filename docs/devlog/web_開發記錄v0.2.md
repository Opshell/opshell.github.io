# 2026-10-02：後台的金額全部改用實際帳單；查估算為什麼差

**使用者**：因為有串實際帳單了，而且和估算的金額落差有點大，目前所有的分析和檢視都用實際帳單的金額下去做計算和呈現，然後檢查估算的部分到底哪裡出問題。

## 金額改用實際帳單（`d65fd96`＋修正）

帳單只細到「哪一天、哪個計價項目」，分不出功能與裝置；估算分得出來但金額不準。所以（`billingCalibration.ts`、`useCostCalibration.ts`）：

- **一天、一段期間的總數直接用帳單**：總覽的「Gemini 實付」、逐日成本表裡帳單已經匯出的日子。
- **每個功能、每台裝置、每次請求 = 估算（美元）× 換算係數 k**，k = 近 90 天、帳單已經匯出的日子裡「實付（台幣）÷ 估算（美元）」，
  同時包含匯率與估算漏掉的部分，所以換算後的總和等於帳單。全後台共用一個 k（模組層級，抓一次）。
- 套用的地方：用量報表（Gemini 成本、每次成本 P95、每點額度值、總成本、每台成本、各模型成本）、總覽（逐日成本、各功能成本圖）、
  用量監看（每台成本與總和）。表頭與小字寫「依實際帳單換算（每 US$1 估算＝NT$k）」。帳單抓不到時退回估算、標「（估）」。
- 金額小於 NT$0.1 的寫到四位（每次請求只有幾毫）。原始的美元估算只留在「Google 實際帳單」那一段當對照。
- 功能名稱補齊：帳單截圖、AI 搜尋、小精靈提醒、後台整理 LINE 回報（後端 `usage/record.go` 的七個）。

## 查估算哪裡出問題

- **單價沒錯**：用 BigQuery 帳單（用使用者的 gcloud，唯讀）反推每個計價項目的單價，跟後端 `usage/pricing.go` 一模一樣
  （3.1 flash lite 0.25／1.50、3.5 flash lite 0.30／2.50 美元每百萬 token），匯率 31.70。**落差是 token 數對不上**。
- **App 沒有直接打 Gemini**（Android 沒有 Gemini SDK）；後端七個功能都有記用量。
- **找到的原因**：
  1. 用量報表**刻意排除測試裝置**（`usage/report.go:121`），但 API 控制台試打 AI 是真的收錢；帳單上 9/29、9/30 特別多，正是 #0074 上線試打的兩天。
  2. **被取消的加問記 0 token**（`gemini/attempt.go`），Google 已經讀完輸入很可能照收。
  3. 同一把金鑰的其他用量（本機開發、AI Studio 網頁），後端看不到。
- 用量報表多「估算跟帳單差多少（近 90 天）」（`BillingReconcile.vue`）：實際是估算的幾倍、換算係數、反推的匯率、
  每個計價項目反推的匯率（都差不到 1% 就標「價目表沒問題」）、被取消的加問次數、上面三個原因、逐日對帳（估算換台幣、實付、差額）。
- 各原因各占多少要後端用自己的表逐日對 token：開了溝通板 **#0085**，附上帳單每天、每個模型的 token，
  並請後端把被取消的加問用贏的那次的輸入 token 補進估算、用量報表另列測試裝置、`models` 多逐日、帳單端點多 `usd_rate`。
- 驗證：照真實帳單的數字做假資料（CDP 攔截帳單與用量報表兩支），各頁金額都變成台幣、逐日表用帳單實付、對帳區塊的倍數與原因正確。

# 2026-10-05：光學台的 O 裡面加「魔法擾動」

**使用者**：很棒很有創意，但白光束進入圓玻璃之後變化不大，出圓玻璃時突然散開，變化太大很怪。
應該要在進入圓玻璃時好像受到魔法干擾一樣，動態的變化，直到出圓玻璃才收束成這些光束。

- O 裡面原本是一條從白漸變到洋紅的直帶，出口才散成六道光。改成**每道光一股光絲**（`prism.ts` 的 `strandAt`）：
  入口 → 漩渦點 → 出口，兩段三次貝茲、接點平滑。漩渦點繞著 O 的中心轉，每股速度與方向不同（有順有逆）、半徑會呼吸，
  光絲被拉著繞圈、互相穿過；出口最後一個控制點在那道光的反方向，所以**出口的切線就是光束的方向**——光是在出口收束成光束。
- 光絲入口是白的、往裡面才變成自己的顏色；裁在玻璃圓裡；外面一層模糊的光暈。入口有一圈圈擴散的漣漪，光點也沿著光絲在 O 裡流（比外面快）。
  滑過一道光時，其他光絲跟著暗下去。關閉動態時是靜止的彎曲光絲。
- 測試：起點是入口、終點是出口、出口方向對準那道光、漩渦點在 O 裡面而且有順有逆、不同時間形狀不同。

# 2026-10-05：光絲分元素（金土火木風水）、出口分開、效能

**使用者**：讓光束有不同的特性，有的剛硬會在裡面折射、有的圓滑、有的柔軟，像五行或地水火風這種世界組成元素的概念；
白色光束是原初，在玻璃裡演化然後散出。但散出不要在同一個點，應該稍微分開，不然最後還是一個點整個散開，稍顯硬。
然後性能有辦法優化嗎？不然一到首頁，電腦風扇直接狂轉。

- **元素**（`prism.ts` 的 `ELEMENTS`、`strandPoints`）：光由上往下照順序分到 金、土、火、木、風、水（照順序不照顏色：分類的顏色會重複）。
  - 金：直線，碰到玻璃內壁反射兩次再直直對準出口（反射角照真的鏡面反射算）
  - 土：粗、往下墜　火：短波長的快速抖動、亮度閃爍　木：兩股反相、越長越大的螺旋（藤蔓互纏）
  - 風：三縷細而淡的絲、一個大而慢的弧　水：一個半波長的正弦，順著流
  - 所有元素都疊在同一條底線上（出口切線對準那道光），擾動用 sin(πs)² 當包絡：出入口的位置與方向不會被弄歪
  - 標籤前面多一個元素字（顏色跟光一樣），螢幕閱讀器念「金：剛硬，在玻璃裡直來直往地折射」
- **出口分開**（`exitsFor`）：各道光的出口沿 O 的右緣分開 0.62 弧度，由上往下，光從各自的出口出去。
- **效能**：原本每一幀都讓 Vue 重畫整個 SVG（45 顆光點、6 股光絲×2、模糊濾鏡、漸層），加上 70 顆星與軌道的 CSS 動畫也讓 SVG 每幀重繪。
  改成會動的（星塵、入口漣漪、光絲、光點）全畫在一張 `<canvas>`，每秒 30 張、不用模糊（光暈用寬而淡的線再描一次）；
  SVG 只放不動的東西，只在滑鼠瞄準、光還在追的時候改；拿掉沒滑鼠時的自動晃動；光的模糊光暈只在滑過時才放；
  「開發中」的脈衝從 box-shadow 改成 transform／opacity（交給合成器）。畫布的顏色從 CSS 變數讀，切深淺色時重讀。
  量測（CDP `Performance.getMetrics`，首頁停 5 秒）：主執行緒 464ms → 87ms、樣式重算 102ms → 12ms；
  GPU 那邊（每幀重算模糊濾鏡）量不到，但已經整個拿掉。

# 2026-10-05：元素的性格與互動

**使用者**：元素名稱不用顯示在標籤前面（程式註解可以有）。圓玻璃內的光束依性質有粗細變化：
金多反射兩次，粗細變化時伴透明度或高光呈現鋒利；土更下沉、多厚度變化，呈現厚重，不太被影響也不太影響他人；
火有一點向上飄（熱氣蒸騰），跟其他光線接觸的地方稍微扭曲別人；木加一點 DNA 雙螺旋的生命感；風經過火的時候抖得更大；
水容易配合其他性質，也不脫離自己的性質；它們再分散一點，給彼此空間發揮。

- 光絲的計算搬到新的 `elements.ts`（`evolve` 一次算全部，因為元素之間會互相影響），`prism.ts` 只留幾何與光的資料。
- **粗細**：光絲改畫成「帶子」（`ribbon`：每一點不同粗細的多邊形，填色），兩端收細（入口是細白光、出口接光的尖端）。
- 金：反射四次；每段像刀刃（中間厚、兩端薄）、中間一條白色高光、反射點輪流閃一下。
- 土：往下沉更多（0.78r），厚度 3.5～7 慢慢起伏；不受熱氣影響，也不扭別人。
- 火：越往後飄越高（熱氣），粗細像火舌一樣跳、整股閃爍；靠近它 26 以內的光絲被熱氣扭（風 10、木與水 3、金 0.8、土 0）。
- 木：雙螺旋，兩股反相、轉到前面粗後面細，每三點一條鹼基對（亮度跟著深度）。
- 風：三縷細絲、一個大而慢的弧；經過火會被扭得最兇。
- 水：保有自己的波浪，靠近別的光絲 30 以內時順著它貼過去（最多 45%），離開了回到自己。
- **分散**：每股有自己的軌道（由上往下 ±0.62r），出口沿右緣分開 0.95 弧度（原本 0.62）。
  軌道、火的上升、木的螺旋改用「前半段 sin、後半段 sin²」的包絡：出口斜率是 0，出口方向不會被帶歪（測試抓到火的出口歪了 0.6 弧度）。
- 標籤前的元素字拿掉；說明文字也不列元素。
- 效能：首頁停 5 秒主執行緒 80ms（上一版 87ms），互動的計算沒有拖慢。

# 2026-10-06：首頁效能（電腦要燒起來）、拿掉光落地的橢圓

**使用者**：太吃效能了吧，電腦要燒起來了，優化一下。光束打下來到標籤，那個橢圓不用。

- **先量對地方**：之前用 1 倍解析度量主執行緒（65ms／5 秒），低估了。改用 2 倍（Retina）、錄 trace 看各執行緒：
  改之前首頁定格後 5 秒，主執行緒約 670ms、合成器約 430ms。用注入 CSS／開關逐一拿掉，找出兩個大頭：
  1. **一直跑的 CSS 動畫**（白光呼吸、往下衝的亮光、分隔線上的光點、「開發中」的脈衝）：就算只動 transform，整頁也得每秒合成 60 次。全拿掉後合成器從 ~450 掉到 ~40。
  2. **畫布**：一張蓋住上半頁的畫布每秒重畫 30 次；而且動畫迴圈每次螢幕刷新都跟瀏覽器要一個 frame（再自己跳過不畫），什麼都不畫也吃掉一大塊。
- **改法**：
  - 白光從畫布搬出來，變成一個 CSS 元素（幾層漸層，不動）；開場時往下長一次。
  - 畫布拆兩張：「靜的」（星塵、一道道光，只在版面、滑過／選了、深淺色改變與開場光往下長的那一秒重畫）、「動的」（只框住 O 到分類那一塊：O 裡的光絲、光上流動的光點，每秒 20 張）。
  - 動畫迴圈改成畫完一張才排下一張（`setTimeout` 到時間再要 frame），不再每次刷新都要。
  - 畫的東西：拿掉 O 裡的 `clip`（量過最貴，每一筆都多一層遮罩；入口的漣漪改成只畫圓裡的那段弧）、拿掉每股光絲外面那層寬而淡的光（木前面那股保留，立體感靠它）、光絲的漸層量版面時做一次就重複用、O 裡沿著光絲跑的小光點拿掉。
  - 分隔線上跑的光點拿掉；「開發中」的脈衝只在游標進到 DinDon 卡片時跳。
  - 光落到分隔線上的橢圓光暈拿掉。
- **結果**（同一台、2 倍解析度、定格後 5 秒，舊版另開一個 worktree 同時量）：主執行緒 ~670 → ~490ms、合成器 ~430 → ~48ms，加起來少一半左右。
